# 5.4 — Propagar el Principal en llamada SÍNCRONA (HTTP)

> **Módulo 5 · Lección 4 de 7**
> El núcleo del módulo. Tu servicio recibe una petición autenticada y, para
> responderla, llama a otro servicio. ¿Cómo no perder al usuario por el camino?

---

## El problema, con un caso concreto

Un cliente llama a `Ordering.API` para crear un pedido. Ordering necesita comprobar
precio y stock, así que llama a `Catalog.API`. La petición original llevaba el token del
usuario; Ordering lo validó y tiene su Principal.

Pero la llamada de **Ordering → Catalog es una petición HTTP nueva**, distinta de la que
hizo el cliente. Si Ordering no hace nada, esa petición sale **sin token**. Catalog la recibe,
no ve credenciales, y responde **401**. El usuario se ha perdido en la frontera entre servicios.

```
   Cliente ──[token]──▶ Ordering.API
                          │  valida ✓  (tiene el Principal)
                          │
                          │  llama a Catalog... pero ¿con qué identidad?
                          ▼
                       Catalog.API
                          │  ¿token? NO → 401  ✗
```

La identidad **no se propaga sola**. Hay que reenviarla deliberadamente. Eso lo programa el dev.

---

## La idea: reenviar el Bearer entrante

El patrón base es simple: **capturar el token que entró** y **adjuntarlo al token que sale**.
El token vive en la cabecera `Authorization: Bearer <token>` de la petición entrante. Lo
leemos de `HttpContext` y lo ponemos en la cabecera de la petición saliente.

La versión ingenua, para entenderlo, sería hacerlo a mano en cada llamada:

```csharp
// NO hagas esto en cada sitio — es para ilustrar la idea
var incomingToken = httpContext.Request.Headers.Authorization.ToString();
httpClient.DefaultRequestHeaders.Add("Authorization", incomingToken);
var response = await httpClient.GetAsync("/catalog/products/123", ct);
```

Funciona, pero es **repetir lo mismo en cada llamada** de cada servicio. El día que a alguien
se le olvide, esa llamada sale sin identidad y falla (o peor, se ejecuta sin el usuario). Eso
es exactamente lo que queremos evitar. Hay un sitio mejor para poner esto: un
**`DelegatingHandler`**.

---

## La solución: un `DelegatingHandler`

Un `DelegatingHandler` es un eslabón en la cadena de procesamiento del `HttpClient`. Toda
petición que sale por ese cliente **pasa por él** antes de viajar. Es el sitio perfecto para
inyectar el token una sola vez, de forma transversal:

```csharp
public sealed class BearerForwardingHandler : DelegatingHandler
{
    private readonly IHttpContextAccessor _accessor;

    public BearerForwardingHandler(IHttpContextAccessor accessor)
        => _accessor = accessor;

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken ct)
    {
        // Token de la petición ENTRANTE (la que atiende este servicio ahora).
        var token = await _accessor.HttpContext!
            .GetTokenAsync("access_token");   // requiere SaveTokens = true (ver abajo)

        if (!string.IsNullOrEmpty(token))
        {
            request.Headers.Authorization =
                new AuthenticationHeaderValue("Bearer", token);
        }

        // Continúa la cadena: la petición ya lleva el token.
        return await base.SendAsync(request, ct);
    }
}
```

Para que `GetTokenAsync("access_token")` funcione, el handler de JWT Bearer debe guardar el
token entrante:

```csharp
.AddJwtBearer(options =>
{
    // ...configuración de 5.2...
    options.SaveToken = true;   // guarda el access_token para poder reenviarlo
});
```

> **Alternativa sin `SaveToken`:** leer la cabecera directa con
> `_accessor.HttpContext!.Request.Headers.Authorization`. Ambas valen; `GetTokenAsync` es más
> explícito sobre la intención.

---

## Enchufar el handler al cliente tipado

Con **Refit** (el cliente declarativo del Módulo 4), se registra así:

```csharp
builder.Services.AddHttpContextAccessor();
builder.Services.AddTransient<BearerForwardingHandler>();

builder.Services
    .AddRefitClient<ICatalogApi>()
    .ConfigureHttpClient(c => c.BaseAddress = new Uri("https://catalog.shopmicro"))
    .AddHttpMessageHandler<BearerForwardingHandler>();   // ← se engancha aquí
```

A partir de aquí, **cualquier** llamada que el dev haga a `ICatalogApi` lleva el token
reenviado **automáticamente**. El dev escribe `await _catalog.GetProductAsync(id)` y no piensa
en credenciales: el handler ya las puso.

```
   Cliente ──[token A]──▶ Ordering.API
                            │ valida ✓
                            │ _catalog.GetProductAsync(id)
                            ▼
                  BearerForwardingHandler
                            │ lee token A de HttpContext
                            │ lo pone en Authorization
                            ▼
                          Catalog.API ──[token A]──▶ valida ✓  ✓
```

---

## Un matiz importante: "actuar como el usuario" vs. "el servicio actúa"

Reenviar el token del usuario significa que Catalog ve la petición **como si la hiciera el
usuario**. Es lo correcto cuando la operación es "en nombre del usuario": comprobar el stock
para *su* pedido.

Hay un caso distinto: tareas de fondo donde **no hay usuario** (un `BackgroundService`, un
relay de mensajes). Ahí no hay token entrante que reenviar. Ese escenario usa identidad de
**servicio a servicio** (el servicio se autentica con sus propias credenciales mediante el
flujo *client credentials*). No lo desarrollamos aquí porque pertenece al territorio de
plataforma, pero conviene saber que existe la distinción: **propagar la identidad del usuario**
(esta lección) frente a **un servicio que se autentica a sí mismo** (sin usuario).

---

## Lo que te llevas de esta lección

- La identidad **no cruza sola** la frontera entre servicios: una llamada saliente es una
  petición nueva, sin token, salvo que tú lo pongas.
- El patrón: **capturar el Bearer entrante y adjuntarlo al saliente**.
- El sitio correcto es un **`DelegatingHandler`**, no cada llamada: transversal, imposible de
  olvidar, enganchado al cliente tipado una sola vez.
- Activa `SaveToken = true` para poder recuperar el token con `GetTokenAsync`.
- Distingue **actuar en nombre del usuario** (reenviar su token) de **un servicio sin usuario**
  (credenciales propias, *client credentials*).
