# 5.3 — Proteger los endpoints: roles y políticas

> **Módulo 5 · Lección 3 de 7**
> Ya validas el token y tienes el Principal. Ahora: ¿quién puede llamar a qué?
> De `[Authorize]` a secas hasta políticas con reglas de negocio.

---

## El escalón más bajo: exigir estar autenticado

Por defecto, un endpoint es público. Para exigir un usuario válido, `[Authorize]` (o el
método equivalente en Minimal API):

```csharp
// Cualquier usuario autenticado puede entrar; los anónimos reciben 401.
app.MapGet("/catalog/products", GetProducts)
   .RequireAuthorization();
```

Sin token válido → **401 Unauthorized**. Con token válido pero sin permiso suficiente (lo
veremos enseguida) → **403 Forbidden**. La distinción importa: 401 es "no sé quién eres",
403 es "sé quién eres y no puedes".

---

## Subir un escalón: autorización por roles

Un **rol** es un claim (`role`) que el IdP mete en el token. "Exige que el usuario tenga el
rol `admin`":

```csharp
app.MapDelete("/catalog/products/{id}", DeleteProduct)
   .RequireAuthorization(policy => policy.RequireRole("admin"));
```

Los roles son el mecanismo más simple, pero también el más rígido. Funcionan cuando la regla
es "los de este grupo sí, el resto no". Para algo más matizado, políticas.

---

## El escalón flexible: políticas

Una **política** es una regla con nombre que puede combinar varios requisitos. Se declaran una
vez al arrancar y se reutilizan por nombre:

```csharp
builder.Services.AddAuthorization(options =>
{
    // Política simple: rol + claim adicional
    options.AddPolicy("CanManageCatalog", policy =>
        policy.RequireRole("admin")
              .RequireClaim("department", "catalog"));

    // Política sobre un claim concreto
    options.AddPolicy("VerifiedCustomer", policy =>
        policy.RequireRole("customer")
              .RequireClaim("email_verified", "true"));
});
```

Y se aplican por nombre:

```csharp
app.MapPost("/catalog/products", CreateProduct)
   .RequireAuthorization("CanManageCatalog");

app.MapPost("/orders", CreateOrder)
   .RequireAuthorization("VerifiedCustomer");
```

La ventaja: la regla vive en **un sitio**, con nombre, y los endpoints la referencian. Si la
política cambia, se cambia en un punto.

---

## Cuando la regla depende de los datos: autorización basada en recursos

Las políticas anteriores solo miran el token. Pero hay reglas que dependen del **recurso
concreto**: *"un cliente solo puede ver SUS pedidos"*. Eso no se puede saber solo con el
token; hay que comparar el `userId` del Principal con el `ownerId` del pedido.

Esto **no** se resuelve con una política declarativa: se resuelve en el **handler**,
comparando. Es lógica de negocio:

```csharp
// En el Handler del slice GetOrder (Vertical Slice):
public async Task<Result> Handle(Query query, CancellationToken ct)
{
    var order = await _repository.GetByIdAsync(query.OrderId, ct);
    if (order is null)
        return Result.NotFound();

    // El Principal llega al handler (lo veremos en 5.4 cómo).
    if (order.CustomerId != query.CurrentUserId)
        return Result.Forbidden();   // sé quién eres, pero este pedido no es tuyo

    return Result.Ok(order.ToResponse());
}
```

La regla general: **lo que depende solo de "quién eres" va en política; lo que depende de
"este recurso concreto es tuyo" va en el handler.** No fuerces una política a hacer consultas
a base de datos; ahí ya es lógica de aplicación.

---

## Aplicado a ShopMicro

| Endpoint | Protección | Tipo |
|---|---|---|
| `GET /catalog/products` | Autenticado | `[Authorize]` |
| `POST /catalog/products` | Política `CanManageCatalog` | rol + claim |
| `DELETE /catalog/products/{id}` | Rol `admin` | rol |
| `POST /orders` | Política `VerifiedCustomer` | rol + claim |
| `GET /orders/{id}` | "es tuyo" | handler (recurso) |

---

## Lo que te llevas de esta lección

- `[Authorize]` / `RequireAuthorization()` exige usuario autenticado. **401** = no sé quién
  eres; **403** = sé quién eres y no puedes.
- **Roles** para reglas de grupo simples; **políticas** para combinar requisitos con nombre y
  reutilizarlas.
- Lo que depende de **quién eres** → política declarativa. Lo que depende de **si este recurso
  concreto es tuyo** → comparación en el **handler**, porque es lógica de negocio.
