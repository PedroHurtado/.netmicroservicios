# 5.6 — Identidad en llamada ASÍNCRONA (mensajería)

> **Módulo 5 · Lección 6 de 7**
> Hasta ahora reenviábamos el token. En mensajería asíncrona eso **no sirve**, y
> entender por qué es la clave de toda la lección.

---

## Por qué el token no sirve en asíncrono

En las llamadas síncronas (5.4 y 5.5) reenviábamos el token porque la llamada ocurría
**ahora**: Ordering llamaba a Catalog y esperaba la respuesta en milisegundos. El token estaba
vigente durante toda la operación.

En mensajería asíncrona el modelo es distinto. Ordering publica un evento `OrderCreated` y
**sigue con su vida**. El evento se queda en el broker (RabbitMQ) hasta que algún consumidor lo
procese: puede ser dentro de 50 milisegundos o, si el consumidor está caído y se reintenta,
dentro de **horas**. Para entonces:

- El token **ya ha caducado** (`exp` es de minutos, no de horas).
- El usuario ya no está "presente"; no hay una petición en curso suya.
- Meter un token de larga duración en un mensaje sería un **agujero de seguridad**: un mensaje
  persistido en una cola, con un token vivo dentro, es justo lo que no quieres que se filtre.

Conclusión: **el token NO viaja en el evento.** Nunca. Si tu instinto es "meto el JWT en el
mensaje", ese instinto está mal calibrado para asíncrono.

```
   Síncrono:                          Asíncrono:
   ┌──────────┐  token vigente        ┌──────────┐
   │ Ordering │ ───[Bearer]──▶        │ Ordering │ ──publica evento──▶ [ broker ]
   └──────────┘     responde ya       └──────────┘                         │
                                                          (minutos... horas)│
                                                                            ▼
                                                                     ┌──────────┐
                       token caducado, usuario ausente   ✗           │ Consumer │
                                                                     └──────────┘
```

---

## Lo que SÍ viaja: el claim necesario en el sobre

Si no viaja el token, ¿cómo sabe el consumidor a qué usuario se refiere el evento? Viaja el
**dato de identidad que el consumidor necesita** —típicamente el `userId` (el `sub`)— como
parte del **sobre** del mensaje. No el token: el claim concreto, ya extraído.

Recuerda del Módulo 4 que en ShopMicro **el `DomainEvent` ES la fila del Outbox**. Cuando
construyes el evento, copias el `userId` del Principal actual a un campo del evento:

```csharp
// En el handler del comando, donde aún tienes el Principal vivo:
public async Task<Result> Handle(CreateOrder.Command cmd, CancellationToken ct)
{
    var order = Order.Create(cmd.Items, cmd.CurrentUserId);

    // El evento lleva QUIÉN lo originó, no el token.
    order.Raise(new OrderCreated(
        OrderId:     order.Id,
        OriginatedBy: cmd.CurrentUserId));   // ← el claim, no el JWT

    await _repository.AddAsync(order, ct);
    return Result.Ok();
}
```

El consumidor, al procesar `OrderCreated`, lee `OriginatedBy` y ya sabe de quién es el pedido.
Sin token, sin caducidad, sin secreto en la cola.

```
   Sobre del evento OrderCreated:
   {
     "orderId":      "...",
     "originatedBy": "a1b2c3d4-..."   ← el claim necesario, extraído
   }                                     (NO hay token aquí)
```

## La distinción que lo ordena todo: actuar vs. registrar

Aquí está la idea que evita la mayoría de los errores de diseño en asíncrono. Hay dos cosas
muy distintas que la gente confunde:

**"Actuar como el usuario"** — ejecutar una operación con los permisos del usuario, como si
él la pidiera ahora. Esto **requiere un token vigente** y autorización en vivo. En asíncrono
**no aplica**: el usuario ya no está, el token caducó. Si un consumidor necesita hacer algo que
exige autorización de usuario, eso es señal de que el diseño está mal: o debería ser síncrono,
o el consumidor actúa con su **propia identidad de servicio**.

**"Registrar quién lo originó"** — dejar constancia de qué usuario disparó la cadena, para
trazabilidad, auditoría o lógica de negocio ("este pedido es de `alice`"). Esto **no requiere
token**: basta el `userId` en el sobre. Es información, no autorización.

| | Actuar como el usuario | Registrar quién lo originó |
|---|---|---|
| ¿Qué necesita? | Token vigente + autorización en vivo | El `userId` en el sobre |
| ¿Vale en asíncrono? | **No** (token caducado, usuario ausente) | **Sí** |
| Para qué sirve | Ejecutar con sus permisos | Auditoría, trazabilidad, negocio |
| Si lo necesitas igual | Identidad de servicio (client credentials) | — |

La regla práctica: **en asíncrono propagas para registrar, no para actuar.** Si te descubres
necesitando "actuar como el usuario" dentro de un consumidor, para y revisa el diseño.

---

## Implicaciones de seguridad

- **No metas el token en el mensaje.** Un mensaje persiste; un token dentro es una credencial
  viva esperando a filtrarse.
- **Mete solo el claim que el consumidor necesita**, no el payload entero del JWT. Minimiza.
- **El consumidor confía en el origen del broker, no en el contenido como credencial.** El
  `userId` del sobre es un dato para registrar, no una autorización. Si el consumidor va a
  ejecutar algo sensible, lo autoriza con la identidad de servicio, no "porque el mensaje dice
  que es de alice".
- **El control de acceso al broker** (quién puede publicar y consumir en cada cola) es la
  frontera de confianza real en asíncrono, y es territorio de plataforma — pero tú debes saber
  que ahí está la línea.

---

## Lo que te llevas de esta lección

- En asíncrono el **token no viaja** en el evento: caduca, y persistirlo en una cola es un
  riesgo.
- Viaja el **claim necesario** (`userId`) en el **sobre** del mensaje, que en ShopMicro es el
  propio `DomainEvent` / fila del Outbox.
- Distingue **actuar como el usuario** (necesita token vigente; no aplica en asíncrono) de
  **registrar quién lo originó** (basta el `userId`; sí aplica).
- En asíncrono propagas identidad **para registrar, no para actuar**.
