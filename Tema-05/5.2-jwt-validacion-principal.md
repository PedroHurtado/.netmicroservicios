# 5.2 — El JWT que llega: validación y materialización del Principal

> **Módulo 5 · Lección 2 de 7**
> El token entra por la puerta. ¿Qué es exactamente, cómo lo valida tu servicio,
> y cómo pasa de ser una cadena de texto a un objeto que tu código puede leer?

---

## Qué es un JWT, por dentro

Un **JWT** (*JSON Web Token*) es una cadena con tres partes separadas por puntos:

```
eyJhbGciOiJSUzI1Ni8...   .   eyJzdWIiOiJhbGljZSI...   .   SflKxwRJSMeKKF2QT4...
└─────── header ───────┘   └─────── payload ───────┘   └──────── firma ───────┘
```

- **Header** — el algoritmo de firma (p. ej. `RS256`) y qué clave se usó (`kid`).
- **Payload** — los **claims**: afirmaciones sobre el usuario. `sub` (el id del usuario),
  `name`, `email`, `role`, `exp` (cuándo caduca), `iss` (quién lo emitió), `aud` (para quién).
- **Firma** — el header y el payload firmados con la clave privada del IdP.

Los dos primeros bloques son **Base64Url, no cifrado**. Cualquiera puede leerlos. Esto
sorprende a mucha gente: **un JWT no es secreto, es verificable**. No metas nada confidencial
en el payload. Su valor no está en ocultar, sino en que **no se puede falsificar**: cambiar
un solo claim invalida la firma, y solo el IdP tiene la clave para firmar de nuevo.

```
   Payload (legible por cualquiera, Base64Url):
   {
     "sub": "a1b2c3d4-...",      ← id del usuario (el Principal)
     "name": "alice",
     "role": ["customer"],
     "iss": "https://identity.shopmicro",
     "aud": "shopmicro-api",
     "exp": 1718200000           ← caducidad (epoch)
   }
```

---

## Qué significa "validar" un token

Validar **no es solo** comprobar la firma. Tu servicio comprueba, en orden:

1. **Firma** — ¿la firmó el IdP? (con la clave pública de JWKS).
2. **Caducidad** (`exp`) — ¿sigue vigente?
3. **Emisor** (`iss`) — ¿lo emitió *nuestro* IdP y no otro?
4. **Audiencia** (`aud`) — ¿está destinado a *este* servicio / API?

Si cualquiera falla, la petición se rechaza con **401 Unauthorized** antes de llegar a tu
endpoint. Tú no escribes ese código: lo hace el middleware de autenticación. Tú lo
**configuras**.

## Configurar JWT Bearer en el servicio

En el `Program.cs` de Catalog.API (o cualquier servicio que deba validar):

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(options =>
    {
        // De dónde sacar las claves públicas (JWKS).
        // El handler descubre el jwks_uri solo a partir de la Authority.
        options.Authority = builder.Configuration["Identity:Authority"];
        // p. ej. "https://identity.shopmicro"

        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = builder.Configuration["Identity:Authority"],

            ValidateAudience = true,
            ValidAudience = "shopmicro-api",

            ValidateLifetime = true,           // comprueba exp
            ValidateIssuerSigningKey = true,   // comprueba la firma con JWKS

            // Sin tolerancia de reloj extra (por defecto son 5 min).
            ClockSkew = TimeSpan.FromSeconds(30)
        };
    });

builder.Services.AddAuthorization();
```

Y en el pipeline, **en este orden** (autenticar antes de autorizar):

```csharp
app.UseAuthentication();   // ¿quién eres? → materializa el Principal
app.UseAuthorization();    // ¿puedes? → aplica [Authorize]
```

Eso es **todo** lo que necesitas para que el servicio valide tokens. El `Authority` le dice
de dónde bajar las claves (descubre el JWKS solo, mediante el documento de configuración
OpenID en `/.well-known/openid-configuration`). El descargador, el caché y la verificación de
firma vienen dados por el framework.

## De cadena de texto a objeto: el `ClaimsPrincipal`

Cuando `UseAuthentication()` valida el token con éxito, **materializa** el Principal: convierte
los claims del payload en un objeto **`ClaimsPrincipal`** y lo deja en `HttpContext.User`.

A partir de ese momento, tu código deja de ver una cadena Base64 y ve un objeto consultable:

```csharp
// Dentro de un endpoint (Minimal API):
app.MapGet("/orders/mine", (HttpContext http) =>
{
    var user = http.User;   // ClaimsPrincipal ya materializado

    var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);  // el "sub"
    var name   = user.Identity?.Name;                             // el "name"
    var isCustomer = user.IsInRole("customer");                   // claim "role"

    return Results.Ok(new { userId, name, isCustomer });
});
```

Inyectar `HttpContext` y leer `http.User` es **la forma en que el dev obtiene el usuario
activo**. Ese `ClaimsPrincipal` es el **Principal**: la representación del usuario
autenticado dentro de tu proceso. Recuérdalo, porque el resto del módulo trata de **propagar
exactamente este objeto** (o el dato clave que contiene) a otros servicios.

---

## Detalle útil: el nombre de los claims

ASP.NET Core, por compatibilidad histórica, **remapea** algunos claims a URIs largas de WS-Fed
(`http://schemas.xmlsoap.org/...`). Por eso `sub` aparece como `ClaimTypes.NameIdentifier`.
Si quieres que los claims lleguen con su nombre original del JWT (`sub`, `role`...), desactiva
el mapeo:

```csharp
// Una sola vez, antes de configurar el handler:
JwtSecurityTokenHandler.DefaultInboundClaimTypeMap.Clear();
```

Es una de esas cosas que cuesta una tarde si no la conoces. Ahora ya la conoces.

---

## Lo que te llevas de esta lección

- Un JWT tiene **header, payload y firma**; el payload es **legible, no secreto** — su valor
  es que **no se puede falsificar**.
- **Validar** = firma + caducidad + emisor + audiencia. Lo configuras; el framework lo ejecuta.
- Configurar JWT Bearer son pocas líneas: `Authority` + `TokenValidationParameters`, más
  `UseAuthentication()` / `UseAuthorization()` **en ese orden**.
- Tras validar, el token se **materializa** en un `ClaimsPrincipal` que vive en
  `HttpContext.User`. Ese es **el Principal**, y es lo que leerás y propagarás.
