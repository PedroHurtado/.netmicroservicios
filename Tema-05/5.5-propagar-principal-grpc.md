# 5.5 — Propagar el Principal en llamada SÍNCRONA (gRPC)

> **Módulo 5 · Lección 5 de 7**
> Mismo problema que 5.4, distinto transporte. En gRPC las credenciales no van
> en el cuerpo del mensaje: viajan en la **metadata**. Y el sitio para inyectarlas
> es un **interceptor**.

---

## Por qué gRPC necesita su propia solución

En el Módulo 4 viste gRPC: contratos en Protobuf, comunicación binaria de alto rendimiento.
El problema de identidad es **el mismo** que en HTTP —una llamada saliente sale sin usuario
salvo que lo pongas— pero las piezas son distintas:

- En HTTP, las credenciales van en la **cabecera `Authorization`** y se inyectan con un
  `DelegatingHandler`.
- En gRPC, las credenciales van en la **metadata** del canal y se inyectan con un
  **interceptor**.

La metadata de gRPC es, conceptualmente, lo mismo que las cabeceras HTTP: pares clave-valor
que acompañan a la llamada sin formar parte del mensaje de negocio. De hecho, gRPC viaja sobre
HTTP/2, así que la metadata acaba siendo cabeceras HTTP/2 por debajo. Por convención, el token
va en la clave `authorization` con el valor `Bearer <token>` — igual que en HTTP.

```
   Mensaje gRPC (Protobuf):  GetProductRequest { id = 123 }   ← negocio
   Metadata:                 authorization: Bearer <token>    ← credenciales (aparte)
```

---

## El interceptor de cliente: inyectar el token al salir

Un **interceptor de cliente** envuelve cada llamada gRPC saliente. Es el equivalente al
`DelegatingHandler`: el punto transversal donde añadir el token una sola vez.

```csharp
public sealed class BearerForwardingInterceptor : Interceptor
{
    private readonly IHttpContextAccessor _accessor;

    public BearerForwardingInterceptor(IHttpContextAccessor accessor)
        => _accessor = accessor;

    public override AsyncUnaryCall<TResponse> AsyncUnaryCall<TRequest, TResponse>(
        TRequest request,
        ClientInterceptorContext<TRequest, TResponse> context,
        AsyncUnaryCallContinuation<TRequest, TResponse> continuation)
    {
        var token = _accessor.HttpContext?
            .Request.Headers.Authorization.ToString();

        if (!string.IsNullOrEmpty(token))
        {
            // Añadir a la metadata de la llamada saliente.
            var headers = context.Options.Headers ?? new Metadata();
            headers.Add("authorization", token);   // ya incluye "Bearer "

            context = new ClientInterceptorContext<TRequest, TResponse>(
                context.Method,
                context.Host,
                context.Options.WithHeaders(headers));
        }

        return continuation(request, context);
    }
}
```

Se registra al configurar el cliente gRPC:

```csharp
builder.Services.AddHttpContextAccessor();

builder.Services
    .AddGrpcClient<Catalog.CatalogClient>(o =>
        o.Address = new Uri("https://catalog.shopmicro"))
    .AddInterceptor<BearerForwardingInterceptor>();   // ← se engancha aquí
```

A partir de aquí, toda llamada al cliente gRPC de Catalog lleva el token en su metadata,
automáticamente. El dev llama al método del contrato y no piensa en credenciales.

## El lado servidor: leer la metadata

Del lado de Catalog (el servicio gRPC que recibe), **no hace falta interceptor para validar**.
Si configuraste JWT Bearer + `[Authorize]` como en 5.2 y 5.3, ASP.NET Core lee la metadata
`authorization`, valida el token y materializa el `ClaimsPrincipal` exactamente igual que con
HTTP. Dentro del método gRPC, el Principal está disponible en el contexto:

```csharp
[Authorize]
public override Task<ProductReply> GetProduct(
    ProductRequest request, ServerCallContext context)
{
    // El Principal ya está materializado por el middleware de autenticación.
    var httpContext = context.GetHttpContext();
    var userId = httpContext.User.FindFirstValue(ClaimTypes.NameIdentifier);

    // ...lógica con el usuario activo...
    return Task.FromResult(reply);
}
```

Es decir: el **cliente** necesita trabajo (el interceptor que inyecta); el **servidor** reutiliza
la misma maquinaria de validación que ya tenías. La simetría con HTTP es total, solo cambian
las piezas concretas.

## HTTP y gRPC, lado a lado

| | HTTP | gRPC |
|---|---|---|
| Dónde van las credenciales | Cabecera `Authorization` | Metadata `authorization` |
| Quién las inyecta (cliente) | `DelegatingHandler` | Interceptor de cliente |
| Cómo se valida (servidor) | JWT Bearer + `[Authorize]` | JWT Bearer + `[Authorize]` (igual) |
| Leer el Principal | `HttpContext.User` | `context.GetHttpContext().User` |

La conclusión práctica: **el concepto es uno solo** —capturar el token entrante e inyectarlo
en la salida, en un punto transversal—, y solo cambia el nombre de la pieza según el transporte.

---

## Lo que te llevas de esta lección

- En gRPC las credenciales viajan en la **metadata**, no en el cuerpo Protobuf; por convención
  en la clave `authorization` con `Bearer <token>`.
- El **interceptor de cliente** es el equivalente al `DelegatingHandler`: inyecta el token en
  cada llamada saliente, una sola vez, de forma transversal.
- El **servidor gRPC** valida con la misma maquinaria JWT Bearer + `[Authorize]` que HTTP;
  no necesita nada especial.
- Mismo concepto que 5.4, distinto transporte. Aprendiste un patrón, no dos.
