# 2.2 Anatomía de un proyecto ASP.NET Core Minimal API

> **Módulo 2 — Fundamentos de .NET para Microservicios**
> Duración estimada: ~40 min

---

## ¿Por qué Minimal API para microservicios?

ASP.NET Core ofrece dos estilos para construir APIs:

- **Controllers (MVC):** el estilo clásico, basado en clases que heredan de `ControllerBase`, con atributos `[HttpGet]`, etc. Más estructura, más ceremonia.
- **Minimal API:** introducido en .NET 6 y maduro en .NET 8. Defines los endpoints directamente con `app.MapGet(...)`, sin clases controladoras.

Para microservicios, **Minimal API es habitualmente la mejor opción**: un microservicio expone pocos endpoints muy cohesionados, y el estilo minimalista reduce el *boilerplate* y arranca más rápido. Usaremos Minimal API en todo el curso. (Los controllers siguen siendo válidos para APIs grandes con muchísimos endpoints.)

## El `Program.cs`: todo empieza aquí

Desde .NET 6, un proyecto usa **top-level statements**: no hay clase `Program` ni método `Main` explícitos. El código se ejecuta de arriba abajo. Hay dos fases muy claras:

```csharp
// ───────── FASE 1: CONFIGURACIÓN (builder) ─────────
// Aquí registramos servicios en el contenedor de DI
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddEndpointsApiExplorer();
builder.Services.AddSwaggerGen();
// ... aquí registraremos EF Core, validadores, clientes HTTP, etc.

var app = builder.Build();   // ← a partir de aquí ya no se registran servicios

// ───────── FASE 2: PIPELINE Y ENDPOINTS (app) ─────────
// Aquí configuramos el pipeline de middleware y los endpoints
if (app.Environment.IsDevelopment())
{
    app.UseSwagger();
    app.UseSwaggerUI();
}

app.UseHttpsRedirection();

app.MapGet("/products", () => "lista de productos");

app.Run();   // ← arranca el servidor y se queda escuchando
```

> **La división mental clave:** *antes* de `builder.Build()` se **registran** capacidades (qué sabe hacer la app). *Después*, se **componen** el pipeline y las rutas (cómo responde a las peticiones). Confundir las dos fases es el error principiante más común.

## Definir endpoints

Los métodos `Map*` cubren los verbos HTTP:

```csharp
app.MapGet("/products", () => productos);                    // listar
app.MapGet("/products/{id}", (int id) => Buscar(id));        // detalle
app.MapPost("/products", (Product p) => Crear(p));           // crear
app.MapPut("/products/{id}", (int id, Product p) => ...);    // actualizar
app.MapDelete("/products/{id}", (int id) => Borrar(id));     // borrar
```

### Binding automático de parámetros

ASP.NET Core resuelve **de dónde sacar cada parámetro** automáticamente:

```csharp
app.MapGet("/products/{id}", (
    int id,                  // ← de la ruta (coincide con {id})
    string? q,               // ← de la query string (?q=...)
    ICatalogService service  // ← inyectado desde el contenedor de DI
) =>
{
    return service.Buscar(id, q);
});
```

El *binding* funciona así, por orden:
- Si el nombre coincide con un `{segmento}` de la ruta → viene de la ruta.
- Tipos primitivos sueltos → de la *query string*.
- Tipos complejos (clases) → del *body* (JSON) por defecto.
- Tipos registrados en DI → se inyectan.

### Devolver respuestas con `Results` / `TypedResults`

Para controlar el código de estado HTTP, usamos los *result helpers*:

```csharp
app.MapGet("/products/{id}", (int id, ICatalogService service) =>
{
    var producto = service.Buscar(id);
    return producto is not null
        ? Results.Ok(producto)        // 200
        : Results.NotFound();          // 404
});

app.MapPost("/products", (Product p, ICatalogService service) =>
{
    var creado = service.Crear(p);
    return Results.Created($"/products/{creado.Id}", creado);  // 201 + Location
});
```

> `TypedResults` es la variante fuertemente tipada de `Results` (p.ej. `TypedResults.Ok(producto)`), recomendada porque facilita los tests y la documentación OpenAPI.

## Organizar endpoints: grupos y archivos separados

Meter 30 endpoints en `Program.cs` no escala. Dos técnicas:

### Route groups

```csharp
var products = app.MapGroup("/products");

products.MapGet("/", GetAll);
products.MapGet("/{id}", GetById);
products.MapPost("/", Create);
// Todos cuelgan de /products y pueden compartir filtros, auth, etc.
```

### Métodos de extensión (el patrón que usaremos)

Sacamos los endpoints a su propio archivo para mantener `Program.cs` limpio:

```csharp
// ProductEndpoints.cs
public static class ProductEndpoints
{
    public static void MapProductEndpoints(this WebApplication app)
    {
        var group = app.MapGroup("/products");
        group.MapGet("/", (ICatalogService s) => s.GetAll());
        group.MapGet("/{id}", (int id, ICatalogService s) => s.GetById(id));
        // ...
    }
}
```

```csharp
// Program.cs — queda limpísimo
app.MapProductEndpoints();
```

## `launchSettings.json`: ejecución local

Define los perfiles de arranque (puertos, entorno) **solo para desarrollo local**. No se usa en producción/contenedores:

```json
{
  "profiles": {
    "Catalog.API": {
      "commandName": "Project",
      "applicationUrl": "http://localhost:5000;https://localhost:5001",
      "environmentVariables": {
        "ASPNETCORE_ENVIRONMENT": "Development"
      }
    }
  }
}
```

## Puntos clave

- **Minimal API** es el estilo idóneo para microservicios: menos ceremonia, arranque rápido.
- `Program.cs` tiene dos fases: **registrar servicios** (antes de `Build()`) y **componer pipeline + endpoints** (después).
- Los parámetros de endpoint se *bindean* automáticamente desde ruta, query, body o DI.
- Usa `Results` / `TypedResults` para controlar el código de estado HTTP.
- Organiza los endpoints con **route groups** y **métodos de extensión** para que `Program.cs` no se infle.
