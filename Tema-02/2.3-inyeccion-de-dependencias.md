# 2.3 Inyección de dependencias y el contenedor de servicios

> **Módulo 2 — Fundamentos de .NET para Microservicios**
> Duración estimada: ~40 min

---

## El problema que resuelve

Imagina un endpoint que necesita acceder a datos. Sin inyección de dependencias, crearías las cosas a mano:

```csharp
// ❌ Acoplamiento fuerte: el endpoint CREA sus dependencias
app.MapGet("/products", () =>
{
    var repo = new ProductRepository(new DbConnection("..."));  // ¡rígido!
    return repo.GetAll();
});
```

Problemas: imposible de testear (no puedes sustituir el repositorio por uno falso), repites la creación por todas partes, y si cambia el constructor de `ProductRepository` tienes que tocar mil sitios.

La **inyección de dependencias (DI)** invierte esto: en vez de que cada componente cree lo que necesita, **lo recibe ya construido desde fuera**. Es uno de los principios SOLID (la "D": *Dependency Inversion*).

> ASP.NET Core tiene DI **integrada de serie**. No necesitas librerías externas (aunque las hay). Es una pieza central del framework, no un añadido.

---

## El contenedor de servicios

El **contenedor de DI** es un registro: le dices "cuando alguien pida la interfaz `X`, dale una instancia de la implementación `Y`". Luego el framework se encarga de construir y entregar las instancias donde hagan falta.

```csharp
// 1. Definimos una abstracción y su implementación
public interface ICatalogService
{
    IEnumerable<Product> GetAll();
}

public class CatalogService : ICatalogService
{
    public IEnumerable<Product> GetAll() => /* ... */;
}

// 2. La REGISTRAMOS en el contenedor (en Program.cs, antes de Build())
builder.Services.AddScoped<ICatalogService, CatalogService>();

// 3. La PEDIMOS donde la necesitemos: llega sola
app.MapGet("/products", (ICatalogService service) => service.GetAll());
//                       └─ el framework inyecta la instancia automáticamente
```

El endpoint ya no sabe **cómo** se construye `CatalogService` ni qué dependencias tiene. Solo declara "necesito un `ICatalogService`" y el contenedor se lo da, resolviendo recursivamente toda la cadena de dependencias.

---

## Los tres ciclos de vida (lifetimes)

Esto es **lo más importante** de la DI y donde están los bugs sutiles. Al registrar un servicio, eliges cuánto vive cada instancia:

| Lifetime | Método | Se crea... | Úsalo para |
|---|---|---|---|
| **Transient** | `AddTransient` | una instancia **nueva cada vez** que se pide | servicios ligeros y sin estado |
| **Scoped** | `AddScoped` | una instancia **por petición HTTP** | lo más común; `DbContext` de EF Core |
| **Singleton** | `AddSingleton` | **una sola instancia** para toda la app | cachés, configuración, clientes reutilizables |

```csharp
builder.Services.AddTransient<IEmailFormatter, EmailFormatter>();
builder.Services.AddScoped<ICatalogService, CatalogService>();
builder.Services.AddSingleton<IPriceCache, PriceCache>();
```

### Visualización de cuándo se crea cada uno

```
Petición HTTP #1          Petición HTTP #2
─────────────────         ─────────────────
Transient: nueva,         Transient: nueva,
 nueva, nueva (cada        nueva... (otra vez
 vez que se inyecta)       desde cero)
Scoped:    UNA para        Scoped:    OTRA para
 toda la petición #1        toda la petición #2
Singleton: la MISMA  ◄──── Singleton: la MISMA
 instancia de siempre       (compartida entre
                            todas las peticiones)
```

## El error clásico: el *captive dependency*

Esto te va a pasar, así que grábatelo. **Nunca inyectes un servicio de vida corta dentro de uno de vida más larga.**

```csharp
// ❌ PELIGRO: un Singleton que captura un Scoped
public class PriceCache  // registrado como Singleton
{
    private readonly AppDbContext _db;  // ¡Scoped! Vive una petición
    public PriceCache(AppDbContext db) => _db = db;
    // El DbContext queda "capturado" para siempre dentro del Singleton.
    // Se usará tras su petición → errores de concurrencia y datos obsoletos.
}
```

El `DbContext` (Scoped) debería morir al acabar la petición, pero el Singleton lo retiene vivo eternamente. Resultado: comportamiento errático y difícil de depurar.

> **Regla:** las dependencias deben ir de **mayor o igual** duración de vida. Un Scoped puede usar un Singleton (✅), pero un Singleton no debe usar un Scoped (❌). Para casos en que un Singleton necesita algo Scoped puntualmente, se usa `IServiceScopeFactory` para crear un *scope* manual.

ASP.NET Core, por suerte, **detecta muchos de estos errores al arrancar** en entorno de desarrollo y lanza una excepción clara.

## Métodos de registro que verás constantemente

Las librerías ofrecen métodos de extensión `Add*` que registran todo lo suyo de una vez:

```csharp
builder.Services.AddDbContext<AppDbContext>(...);   // EF Core (Módulo 6)
builder.Services.AddHttpClient<CatalogClient>();    // clientes HTTP (Módulo 4)
builder.Services.AddAuthentication().AddJwtBearer(); // seguridad (Módulo 5)
builder.Services.AddValidatorsFromAssembly(...);     // FluentValidation (Módulo 3)
```

Y un patrón muy útil para mantener `Program.cs` ordenado: agrupar tus propios registros en un método de extensión.

```csharp
public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddCatalogServices(this IServiceCollection services)
    {
        services.AddScoped<ICatalogService, CatalogService>();
        services.AddScoped<IProductRepository, ProductRepository>();
        return services;
    }
}

// Program.cs
builder.Services.AddCatalogServices();  // limpio y legible
```

---

## Puntos clave

- La DI **invierte** la creación de dependencias: los componentes las **reciben**, no las crean.
- ASP.NET Core trae el contenedor de DI **integrado**; registras en `builder.Services`.
- Tres lifetimes: **Transient** (cada vez), **Scoped** (por petición), **Singleton** (uno para todo).
- El `DbContext` de EF Core va casi siempre como **Scoped**.
- Evita el **captive dependency**: nunca metas un Scoped dentro de un Singleton.
- Agrupa registros en métodos de extensión `Add*` para mantener `Program.cs` limpio.
