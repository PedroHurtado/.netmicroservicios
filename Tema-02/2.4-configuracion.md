# 2.4 Configuración (`appsettings`, entornos, variables de entorno, `IOptions`)

> **Módulo 2 — Fundamentos de .NET para Microservicios**
> Duración estimada: ~40 min

---

## Por qué importa especialmente en microservicios

Un microservicio se ejecuta en muchos entornos (tu máquina, CI, *staging*, producción) y en contenedores donde la configuración llega **desde fuera** (variables de entorno, *secrets* de Kubernetes). Entender bien el sistema de configuración de .NET es imprescindible para que el mismo binario funcione en todas partes sin recompilar.

---

## El sistema de configuración por capas

.NET construye la configuración **apilando varias fuentes**, donde **cada fuente sobrescribe a la anterior**. Este es el orden por defecto (de menor a mayor prioridad):

```
1. appsettings.json                    (base, en el repo)
2. appsettings.{Environment}.json      (p.ej. appsettings.Development.json)
3. User secrets                        (solo en Development — ver Módulo 5)
4. Variables de entorno                ◄── clave en contenedores
5. Argumentos de línea de comandos     (máxima prioridad)
        │
        ▼
  IConfiguration final (las de abajo ganan)
```

Esto es potentísimo: defines valores por defecto en `appsettings.json` y los **sobreescribes en producción con variables de entorno**, sin tocar el código ni la imagen del contenedor.

---

## `appsettings.json`

Un archivo JSON jerárquico:

```json
{
  "Logging": {
    "LogLevel": { "Default": "Information" }
  },
  "ConnectionStrings": {
    "CatalogDb": "Host=localhost;Database=catalog;Username=postgres;Password=dev"
  },
  "CatalogSettings": {
    "PageSize": 20,
    "EnableCache": true
  }
}
```

### Entornos

ASP.NET Core lee la variable `ASPNETCORE_ENVIRONMENT` para saber en qué entorno está (`Development`, `Staging`, `Production`...). Según su valor, carga además el `appsettings.{Environment}.json` correspondiente, que sobreescribe al base.

```csharp
if (app.Environment.IsDevelopment())
{
    app.UseSwaggerUI();   // Swagger solo en desarrollo, por ejemplo
}
```

## Leer configuración: las formas

### Acceso directo (rápido, pero poco recomendable a gran escala)

```csharp
var pageSize = builder.Configuration.GetValue<int>("CatalogSettings:PageSize");
var conn     = builder.Configuration.GetConnectionString("CatalogDb");
//                                              ↑ los : navegan la jerarquía JSON
```

### El patrón `IOptions<T>` (el recomendado)

En lugar de leer claves sueltas con *strings* por todo el código, **enlazas una sección a una clase fuertemente tipada**:

```csharp
// 1. Una clase que modela la sección de config
public class CatalogSettings
{
    public int PageSize { get; set; }
    public bool EnableCache { get; set; }
}

// 2. La enlazamos en Program.cs
builder.Services.Configure<CatalogSettings>(
    builder.Configuration.GetSection("CatalogSettings"));

// 3. La inyectamos donde haga falta vía IOptions<T>
app.MapGet("/products", (IOptions<CatalogSettings> options, ICatalogService s) =>
{
    var settings = options.Value;        // ← la instancia tipada
    return s.GetPage(settings.PageSize);
});
```

Ventajas: tipado fuerte (nada de *strings* mágicos repetidos), validación, y se integra con la DI.

### Variantes de IOptions

| Interfaz | Comportamiento | Lifetime |
|---|---|---|
| `IOptions<T>` | Valor fijo, calculado una vez | Singleton |
| `IOptionsSnapshot<T>` | Se recalcula **por petición** (recoge cambios) | Scoped |
| `IOptionsMonitor<T>` | Notifica cambios en caliente | Singleton |

Para la mayoría de casos, `IOptions<T>` es suficiente.

## Variables de entorno: el puente hacia los contenedores

En contenedores y Kubernetes, la configuración casi siempre llega por **variables de entorno**. La convención para representar la jerarquía JSON es el **doble guion bajo** `__`:

```bash
# Esto sobreescribe CatalogSettings:PageSize del appsettings.json
export CatalogSettings__PageSize=50

# Esto sobreescribe la cadena de conexión
export ConnectionStrings__CatalogDb="Host=db;Database=catalog;..."
```

En un `docker-compose.yml` (Módulo 7) se verá así:

```yaml
services:
  catalog-api:
    image: shopmicro/catalog
    environment:
      - ASPNETCORE_ENVIRONMENT=Production
      - ConnectionStrings__CatalogDb=Host=postgres;Database=catalog;Username=app;Password=...
      - CatalogSettings__PageSize=50
```

> **Idea central:** el **mismo binario y la misma imagen** se comportan distinto en cada entorno solo cambiando variables de entorno. Nunca hardcodees configuración que cambie entre entornos.

## Validación de configuración al arranque

Una buena práctica en microservicios: que el servicio **falle rápido al arrancar** si le falta configuración crítica, en vez de petar a mitad de una petición:

```csharp
builder.Services.AddOptions<CatalogSettings>()
    .Bind(builder.Configuration.GetSection("CatalogSettings"))
    .ValidateDataAnnotations()
    .Validate(s => s.PageSize > 0, "PageSize debe ser mayor que 0")
    .ValidateOnStart();   // ← valida al arrancar, no en la primera petición
```

## Puntos clave

- La configuración se construye **por capas**; cada fuente sobrescribe a la anterior.
- Orden de prioridad: appsettings → appsettings.{Env} → user-secrets → **variables de entorno** → CLI.
- `ASPNETCORE_ENVIRONMENT` selecciona el `appsettings.{Environment}.json` a cargar.
- Usa el patrón **`IOptions<T>`** para configuración tipada en vez de leer *strings* sueltos.
- En contenedores, la jerarquía JSON se mapea con **`__`** en variables de entorno.
- Valida la configuración con **`ValidateOnStart()`** para fallar rápido.
