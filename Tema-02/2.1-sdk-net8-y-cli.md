# 2.1 El SDK de .NET 8 y la CLI (`dotnet new`, `build`, `run`)

> **Módulo 2 — Fundamentos de .NET para Microservicios**
> Duración estimada: ~35 min

---

## SDK vs. Runtime

Dos cosas distintas que conviene no confundir:

- **Runtime** (.NET Runtime): lo necesario para **ejecutar** una aplicación .NET ya compilada. Es lo que instalas en un servidor de producción (o lo que va dentro de la imagen de contenedor).
- **SDK** (Software Development Kit): incluye el runtime **más** todas las herramientas para **desarrollar**: el compilador, la CLI `dotnet`, las plantillas de proyecto, etc. Es lo que instalas en tu máquina de desarrollo.

Para el curso necesitas el **SDK de .NET 8**. Compruébalo:

```bash
dotnet --version
# Debería mostrar algo como 8.0.xxx

dotnet --list-sdks      # todos los SDK instalados
dotnet --list-runtimes  # todos los runtimes instalados
```

> **Nota sobre versiones:** usamos .NET 8 (LTS) por ser el más extendido y documentado en el ecosistema de microservicios. Su soporte acaba en noviembre de 2026; en el Módulo 7 veremos la ruta de migración a .NET 10. El código es prácticamente idéntico entre versiones.

## La CLI `dotnet`: tu herramienta principal

Todo el ciclo de desarrollo se puede hacer desde la línea de comandos, sin depender del IDE. Esto es **fundamental** en microservicios: los pipelines de CI/CD y los Dockerfiles usan exactamente estos comandos.

### `dotnet new` — crear proyectos

```bash
# Ver las plantillas disponibles
dotnet new list

# Crear una Web API mínima (la que usaremos para los servicios)
dotnet new web -n Catalog.API

# Crear una solución que agrupe varios proyectos
dotnet new sln -n ShopMicro

# Añadir un proyecto a la solución
dotnet sln add Catalog.API/Catalog.API.csproj
```

Plantillas que usaremos en el curso:

| Plantilla | Comando | Para qué |
|---|---|---|
| Web vacía / Minimal API | `dotnet new web` | Nuestros microservicios |
| Solución | `dotnet new sln` | Agrupar todos los servicios |
| Class Library | `dotnet new classlib` | Código compartido (contratos) |
| gitignore | `dotnet new gitignore` | Ignorar `bin/`, `obj/`, etc. |

### `dotnet build` — compilar

```bash
dotnet build
# Compila el proyecto/solución y muestra errores y warnings
```

### `dotnet run` — ejecutar

```bash
dotnet run
# Compila (si hace falta) y ejecuta. Para desarrollo local.

# Con recarga en caliente al guardar cambios:
dotnet watch run
```

`dotnet watch run` es tu mejor amigo en desarrollo: recompila y reinicia automáticamente al detectar cambios en el código.

### Otros comandos que usaremos

```bash
dotnet add package <Nombre>     # añadir un paquete NuGet
dotnet restore                  # restaurar dependencias
dotnet test                     # ejecutar tests
dotnet publish -c Release       # generar artefactos para producción
```

## Anatomía de un proyecto recién creado

Tras `dotnet new web -n Catalog.API`, obtienes:

```
Catalog.API/
├── Catalog.API.csproj      ← definición del proyecto y dependencias
├── Program.cs              ← punto de entrada (todo arranca aquí)
├── appsettings.json        ← configuración
├── appsettings.Development.json
└── Properties/
    └── launchSettings.json ← perfiles de ejecución local (puertos, etc.)
```

### El `.csproj`

Es un XML que define cómo se construye el proyecto:

```xml
<Project Sdk="Microsoft.NET.Sdk.Web">

  <PropertyGroup>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>            <!-- referencias nulas seguras -->
    <ImplicitUsings>enable</ImplicitUsings> <!-- usings automáticos comunes -->
  </PropertyGroup>

  <!-- Las dependencias NuGet aparecerán aquí: -->
  <ItemGroup>
    <PackageReference Include="FluentValidation" Version="11.x.x" />
  </ItemGroup>

</Project>
```

Dos opciones que conviene conocer:
- **`ImplicitUsings`**: añade automáticamente los `using` más comunes (`System`, `System.Linq`...), por eso muchos archivos no los declaran.
- **`Nullable`**: activa el análisis de nulabilidad, que ayuda a evitar los temidos `NullReferenceException`.

## El ciclo de trabajo típico

```bash
# 1. Crear la solución y el primer servicio
dotnet new sln -n ShopMicro
dotnet new web -n Catalog.API
dotnet sln add Catalog.API/Catalog.API.csproj

# 2. Entrar y ejecutar con recarga en caliente
cd Catalog.API
dotnet watch run

# 3. (en otra terminal) probar el endpoint
curl http://localhost:5000/
```

---

## Puntos clave

- El **SDK** es para desarrollar; el **runtime** es para ejecutar (importante para Docker).
- La CLI `dotnet` cubre todo el ciclo: `new`, `build`, `run`, `test`, `publish`.
- `dotnet watch run` recompila y reinicia al guardar — esencial en desarrollo.
- El `.csproj` define *target framework* y dependencias; `ImplicitUsings` y `Nullable` vienen activados.
- Estos mismos comandos son los que usarán nuestros Dockerfiles y pipelines (Módulo 7).
