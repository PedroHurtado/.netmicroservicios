# 2.5 Logging estructurado y *middleware pipeline*

> **Módulo 2 — Fundamentos de .NET para Microservicios**

Este punto cubre dos temas que se tocan: el **pipeline de middleware** (cómo se procesa cada petición) y el **logging estructurado** (cómo dejamos rastro de lo que pasa). Ambos son la base de la observabilidad que profundizaremos en el Módulo 7.

## Parte 1: El middleware pipeline

### Qué es

Cada petición HTTP que entra atraviesa una **cadena de componentes** llamados *middleware*, uno tras otro, antes de llegar a tu endpoint. Y la respuesta los vuelve a atravesar en sentido inverso. Es como una cebolla:

```
Petición →  [Logging] → [HTTPS] → [Auth] → [tu endpoint]
                                                  │
Respuesta ← [Logging] ← [HTTPS] ← [Auth] ←────────┘
```

Cada middleware puede: hacer algo con la petición, decidir pasarla al siguiente (`next`), o **cortocircuitar** (responder sin llamar al siguiente).

### El orden IMPORTA (mucho)

El pipeline se construye en `Program.cs` con los métodos `Use*`, y **se ejecutan en el orden en que los escribes**. Esto es fuente de bugs si te equivocas:

```csharp
var app = builder.Build();

app.UseHttpsRedirection();   // 1º
app.UseAuthentication();     // 2º — ¿quién eres?
app.UseAuthorization();      // 3º — ¿puedes hacer esto?
app.MapProductEndpoints();   // 4º — finalmente, tu lógica

app.Run();
```

> Si pones `UseAuthorization()` **antes** que `UseAuthentication()`, la autorización se ejecutaría sin saber aún quién es el usuario. El framework te avisa de algunos de estos errores, pero no de todos. **Regla mnemotécnica:** autenticar (saber quién eres) siempre va antes que autorizar (saber qué puedes hacer).

### Escribir tu propio middleware

Para lógica transversal (que afecta a todas las peticiones). Ejemplo: medir cuánto tarda cada petición.

```csharp
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next();                    // ← pasa al siguiente middleware/endpoint
    sw.Stop();
    Console.WriteLine($"{context.Request.Path} tardó {sw.ElapsedMilliseconds}ms");
});
```

En el Módulo 3 usaremos este mismo concepto para el **manejo global de errores** (`ProblemDetails`), que es un middleware que envuelve todo y captura excepciones.

## Parte 2: Logging estructurado

### Logging tradicional vs. estructurado

El logging "de toda la vida" produce **texto plano**:

```
Producto 42 no encontrado para el usuario juan
```

El **logging estructurado** produce **datos con campos nombrados**: el mensaje y sus parámetros se guardan por separado, de forma que luego puedes **buscar y filtrar** por esos campos.

```csharp
logger.LogWarning("Producto {ProductId} no encontrado para usuario {User}", 42, "juan");
```

Esto genera un registro con campos `ProductId=42` y `User=juan`. En microservicios esto es **crítico**: con decenas de servicios escupiendo logs a un sistema central, necesitas poder consultar *"dame todos los logs donde ProductId=42, de cualquier servicio"*. Con texto plano eso es imposible; con logs estructurados es una consulta trivial.

> **Detalle importante:** usa **plantillas con marcadores** `{Nombre}`, **no interpolación de strings**. Es decir, `LogWarning("... {ProductId}", id)` y **no** `LogWarning($"... {id}")`. Solo la primera forma preserva la estructura; la interpolación la destruye y se queda en texto plano.

### Cómo se usa: `ILogger<T>` por DI

El logger se inyecta como cualquier otra dependencia:

```csharp
app.MapGet("/products/{id}", (int id, ICatalogService s, ILogger<Program> logger) =>
{
    logger.LogInformation("Buscando producto {ProductId}", id);

    var producto = s.GetById(id);
    if (producto is null)
    {
        logger.LogWarning("Producto {ProductId} no encontrado", id);
        return Results.NotFound();
    }
    return Results.Ok(producto);
});
```

### Niveles de log

De menos a más grave. Configurables por entorno (en `appsettings.json`):

| Nivel | Cuándo usarlo |
|---|---|
| `Trace` | Detalle finísimo de depuración (nunca en producción) |
| `Debug` | Información de depuración para desarrollo |
| `Information` | Flujo normal: "petición recibida", "pedido creado" |
| `Warning` | Algo inesperado pero recuperable |
| `Error` | Un fallo en la operación actual |
| `Critical` | El sistema entero está en peligro |

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  }
}
```

### Scopes: añadir contexto a un bloque de logs

Los *scopes* adjuntan datos comunes a todos los logs que ocurran dentro de un bloque — útil para correlacionar:

```csharp
using (logger.BeginScope("Pedido {OrderId}", orderId))
{
    logger.LogInformation("Validando líneas");   // llevará OrderId adjunto
    logger.LogInformation("Calculando total");    // este también
}
```

Esto enlaza con la idea de **correlación entre servicios** del Módulo 7: cuando una petición salta entre servicios, queremos un identificador común (*trace id*) que aparezca en todos los logs de todos los servicios involucrados.

### Hacia producción: Serilog y salida a JSON

El logging integrado de .NET es bueno, pero en producción se suele usar **Serilog** (la librería estándar de facto) para enviar logs estructurados en formato JSON a sistemas centralizados (Seq, Elasticsearch, Loki...). Lo veremos en el Módulo 7. Un anticipo:

```csharp
// Con Serilog, los logs salen como JSON con todos sus campos,
// listos para ingerir en un sistema central de búsqueda.
builder.Host.UseSerilog((ctx, cfg) =>
    cfg.ReadFrom.Configuration(ctx.Configuration)
       .WriteTo.Console(new JsonFormatter()));
```

## Cómo encajan ambos temas

El logging y el middleware se combinan en un patrón omnipresente: un middleware que registra cada petición entrante y saliente, sentando las bases de la **observabilidad**. ASP.NET Core ya trae uno integrado, y en el Módulo 7 lo ampliaremos con **trazas distribuidas (OpenTelemetry)** para seguir una petición a través de todo ShopMicro.

---

## Puntos clave

- Cada petición atraviesa el **pipeline de middleware**; el **orden de los `Use*` importa**.
- Autenticación siempre **antes** que autorización.
- Un middleware puede continuar (`next`) o **cortocircuitar** la petición.
- El **logging estructurado** guarda campos nombrados, no texto plano — esencial para buscar entre muchos servicios.
- Usa plantillas `{Marcador}`, **nunca** interpolación `$"..."`, para preservar la estructura.
- Inyecta `ILogger<T>` por DI; elige el **nivel** adecuado; usa **scopes** para correlacionar.
- En producción: Serilog + salida JSON a un sistema central (Módulo 7).
