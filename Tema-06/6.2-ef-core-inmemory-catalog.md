## Qué es EF Core y qué papel juega

**Entity Framework Core** es el ORM oficial de .NET: mapea clases C# a tablas y traduce LINQ a SQL.
En nuestra arquitectura, EF Core vive **exclusivamente en la capa de infraestructura** del
servicio. El dominio no lo conoce; lo veremos con detalle en 6.3 y 6.4.

Las dos piezas que hay que entender:

- **`DbContext`** — la unidad de trabajo y la sesión con la base de datos. Representa una
  transacción lógica: acumulas cambios y los confirmas con `SaveChangesAsync()`.
- **`DbSet<T>`** — una colección consultable que representa una "tabla" de entidades de tipo `T`.

```
┌──────────────────────────────────────────────┐
│              CatalogDbContext                  │
│                                                │
│   DbSet<PizzaEf>      Pizzas      ─────▶ tabla │
│   DbSet<IngredientEf> Ingredients ─────▶ tabla │
│                                                │
│   SaveChangesAsync()  ──▶ confirma los cambios │
└──────────────────────────────────────────────┘
```

---

## Por qué InMemory en este módulo

EF Core soporta varios **proveedores**: SQL Server, PostgreSQL (Npgsql), SQLite… y un proveedor
**InMemory** pensado para pruebas y prototipos. Lo elegimos aquí porque:

- **No requiere infraestructura:** ni instalar Postgres, ni contenedores, ni cadenas de conexión.
- El **código de los repositorios es idéntico** sea cual sea el proveedor. Solo cambia una línea
  en el arranque.
- Nos deja concentrarnos en lo que importa en este módulo: el **diseño ISP de la capa de datos**.

> ⚠️ **InMemory no es una base de datos relacional.** No valida claves foráneas, no ejecuta SQL y
> no es transaccional de verdad. Sirve para aprender y para tests, **no para producción**. En
> producción se cambia el proveedor (ver más abajo).

## Registro del DbContext (InMemory)

`Program.cs` de Catalog.API:

```csharp
var builder = WebApplication.CreateBuilder(args);

// --- Persistencia: EF Core InMemory ---------------------------------
builder.Services.AddDbContext<CatalogDbContext>(options =>
    options.UseInMemoryDatabase("catalog"));   // ← único punto que cambia vs. PostgreSQL

// ... registro de repositorios (lo veremos en 6.4)

var app = builder.Build();
```

El día que quieras PostgreSQL **solo cambia esa línea**:

```csharp
// builder.Services.AddDbContext<CatalogDbContext>(options =>
//     options.UseNpgsql(builder.Configuration.GetConnectionString("Catalog")));
```

El resto del servicio —repositorios, mappers, dominio, endpoints— **no se entera**.

## El DbContext de Catalog

```csharp
using Microsoft.EntityFrameworkCore;

public sealed class CatalogDbContext : DbContext
{
    public CatalogDbContext(DbContextOptions<CatalogDbContext> options)
        : base(options) { }

    public DbSet<PizzaEf> Pizzas => Set<PizzaEf>();
    public DbSet<IngredientEf> Ingredients => Set<IngredientEf>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // La relación N:M Pizza–Ingredient se configura aquí.
        // La veremos al detalle en 6.4, junto a la clase PizzaEf.
        modelBuilder.Entity<PizzaEf>()
            .HasMany(p => p.Ingredients)
            .WithMany();
    }
}
```

> **Nota sobre migraciones.** Con un proveedor relacional (PostgreSQL, SQL Server) usaríamos
> `dotnet ef migrations add` y `dotnet ef database update` para versionar el esquema. Con
> **InMemory no hay migraciones** —la "base de datos" se crea vacía en cada arranque—, por eso en
> este módulo no entramos en ese flujo. El concepto queda anotado: *cada servicio versiona su
> propio esquema de forma independiente* (coherente con 6.1).

## Sembrar datos para la clase

Como InMemory arranca vacío, conviene un *seed* para tener pizzas con las que jugar en el aula:

```csharp
public static class CatalogSeed
{
    public static async Task SeedAsync(CatalogDbContext db)
    {
        if (await db.Pizzas.AnyAsync()) return;   // idempotente

        var margarita = new PizzaEf(
            Guid.NewGuid(),
            "Margarita",
            "La clásica de toda la vida",
            "https://shopmicro/img/margarita.png",
            new HashSet<IngredientEf>());

        db.Pizzas.Add(margarita);
        await db.SaveChangesAsync();
    }
}
```

Y en el arranque:

```csharp
using (var scope = app.Services.CreateScope())
{
    var db = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
    await CatalogSeed.SeedAsync(db);
}
```

## Puntos clave

- **EF Core vive solo en infraestructura.** El dominio nunca lo referencia.
- `DbContext` = unidad de trabajo; `DbSet<T>` = tabla consultable.
- **InMemory** elimina la infraestructura y deja el foco en el diseño; el código de repositorios es
  el mismo que con PostgreSQL.
- **Cambiar de proveedor es una sola línea** en `Program.cs`.
- InMemory **no tiene migraciones** ni garantías relacionales: vale para aprender y para tests, no
  para producción.
