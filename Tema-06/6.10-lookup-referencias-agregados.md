# 6.10 — Lookup: resolver referencias entre agregados (OCP)

> **Módulo 6 · Lección 10 de 9** *(adenda)*
> **Duración estimada:** ~30 min
> **Tipo:** Teoría + código
> **Requisitos:** 6.3 (núcleo ISP) y 6.4 (agregado Pizza)

---

## El problema que resuelve

Cuando creamos una `Pizza`, el comando **no trae objetos `Ingredient` completos**: trae una lista
de **ids** de ingredientes. Alguien tiene que **resolver esos ids a entidades de dominio reales** —
y verificar que existen — antes de construir el agregado.

```
   Command de "crear pizza"                Agregado de dominio
   ────────────────────────                ───────────────────
   Name = "Cuatro quesos"                   Pizza
   IngredientIds = [ g1, g2, g3, g4 ]  ──▶  Ingredients = { Mozzarella, ... }
                       │                          ▲
                       │   ¿quién traduce          │
                       └── ids → Ingredient? ──────┘
```

Podríamos inyectar `IGetIngredient` directamente en el handler de pizza y llamarlo en bucle. Pero
fíjate en lo que pasaría a medida que crecen los agregados que **referencian** a otros:

- El handler de Pizza necesita resolver `Ingredient`.
- Mañana, un agregado `Menu` necesita resolver `Pizza` **y** `Bebida`.
- Pasado, `Pedido` necesita resolver `Producto`, `Cliente`, `Cupón`…

Cada caso acabaría inyectando y cableando a mano sus resolvedores. Hay un patrón mejor: un
**mecanismo único de resolución de referencias por tipo**, abierto a extensión y cerrado a
modificación (**OCP**, la "O" de SOLID).

---

## La idea: `ILookup<T>` + `LookupResolver`

Dos piezas, en el núcleo del dominio (`Core/Lookup`):

- **`ILookup<T>`** — sabe resolver **un** agregado destino de FK por id. Cada agregado que pueda ser
  *referenciado* por otro registra su propia implementación.
- **`LookupResolver`** — punto único. Recibe **todos** los `ILookup` registrados, los **indexa por
  el tipo que resuelven** y ofrece `FindAsync<T>(id)` / `FindAllAsync<T>(ids)`.

```
            ┌─────────────────────────────────────────────┐
            │              LookupResolver                  │
            │   índice:  Type ─────────────▶ ILookup       │
            │            Ingredient ──────▶ IngredientLookup│
            │            Bebida     ──────▶ BebidaLookup    │
            │            ...        ──────▶ ...             │
            └───────────────────┬─────────────────────────┘
                                │  resolver.FindAllAsync<Ingredient>(ids)
                                ▼
              devuelve  ISet<Ingredient>  (o lanza si algún id no existe)

   Añadir un nuevo destino (p. ej. Topping):
       basta registrar un ILookup<Topping> nuevo.
       LookupResolver NO se modifica  →  Open/Closed.
```

> **Detalle de diseño.** La interfaz `ILookup<T>` **no declara qué tipo resuelve**: el resolver lo
> **infiere del propio genérico** por reflexión al construir el índice. Así la interfaz queda
> reducida a lo esencial — una sola operación, `FindAsync` — y el implementador no tiene que repetir
> el tipo por ningún sitio.

---

## La interfaz `ILookup<T>`

```csharp
namespace ShopMicro.Core.Lookup;

/// <summary>
/// Interfaz marcadora (vacía). No aporta métodos: existe solo para que el contenedor de
/// dependencias pueda recoger TODOS los lookups con una sola consulta —
/// GetServices&lt;ILookupMarker&gt;()— sin tener que registrar cada uno como object.
/// </summary>
public interface ILookupMarker { }

/// <summary>
/// Resuelve una referencia (FK) a un agregado de dominio por id. Cada agregado que sea
/// destino de FK registra su propia implementación de ILookup&lt;T&gt;.
///
/// FindAsync devuelve T o lanza EntityNotFoundException si no existe — misma semántica que
/// IGet (lección 6.3): nunca null, nunca opcional.
/// </summary>
public interface ILookup<T> : ILookupMarker
{
    Task<T> FindAsync(Guid id);
}
```

Una sola operación útil. El tipo que resuelve se infiere del genérico; no se declara aquí. La
marcadora `ILookupMarker` no se implementa a mano: viene "gratis" por extender `ILookup<T>`.

> **La técnica de la interfaz marcadora.** Una interfaz vacía sirve de **etiqueta** común a un
> conjunto de tipos heterogéneos para que el contenedor los recoja juntos. Es el mismo truco que
> usaremos para **auto-registrar las Minimal APIs** desde `Program`: una marcadora `IEndpoint`, cada
> slice la implementa, y un único barrido las registra todas sin tocar `Program` por cada endpoint
> nuevo. Apréndela bien aquí porque la reutilizaremos.

## El `LookupResolver`

```csharp
namespace ShopMicro.Core.Lookup;

/// <summary>
/// Punto único para resolver FKs por tipo de agregado. Recibe por inyección de colección
/// todos los ILookup&lt;T&gt; registrados y los indexa por el tipo T que resuelve cada uno
/// (inferido del genérico, sin que la interfaz tenga que declararlo).
///
/// Añadir un nuevo destino de FK NO obliga a tocar esta clase: basta registrar un nuevo
/// ILookup&lt;T&gt; en el contenedor. Eso es Open/Closed (OCP) en la práctica.
/// </summary>
public sealed class LookupResolver
{
    private readonly Dictionary<Type, ILookupMarker> _lookups;

    // Recibe todos los lookups del contenedor vía la marcadora. Cada uno cierra
    // ILookup<T> sobre un T distinto; el tipo concreto se recupera justo abajo, al indexar.
    public LookupResolver(IEnumerable<ILookupMarker> lookups)
        => _lookups = lookups.ToDictionary(TargetTypeOf, lookup => lookup);

    /// <summary>Extrae el T de un objeto que implementa ILookup&lt;T&gt;.</summary>
    private static Type TargetTypeOf(ILookupMarker lookup)
    {
        var iface = lookup.GetType().GetInterfaces()
            .First(i => i.IsGenericType &&
                        i.GetGenericTypeDefinition() == typeof(ILookup<>));
        return iface.GetGenericArguments()[0];   // el T de ILookup<T>
    }

    /// <summary>Resuelve una referencia. Lanza si el id no existe (propaga de FindAsync).</summary>
    public Task<T> FindAsync<T>(Guid id)
    {
        if (!_lookups.TryGetValue(typeof(T), out var lookup))
            throw new NoLookupRegisteredException(typeof(T));

        return ((ILookup<T>)lookup).FindAsync(id);   // cast encapsulado AQUÍ, no en el llamante
    }

    /// <summary>
    /// Resuelve una colección de referencias. Si algún id no existe, FindAsync lanza
    /// EntityNotFoundException → la operación entera falla (no devuelve resultados parciales).
    /// </summary>
    public async Task<ISet<T>> FindAllAsync<T>(IEnumerable<Guid> ids)
    {
        var result = new HashSet<T>();
        foreach (var id in ids)
            result.Add(await FindAsync<T>(id));
        return result;
    }
}
```

```csharp
namespace ShopMicro.Core.Lookup;

/// <summary>Se lanza al pedir un tipo para el que no hay ILookup registrado (fallo de cableado).</summary>
public sealed class NoLookupRegisteredException : Exception
{
    public NoLookupRegisteredException(Type type)
        : base($"No hay Lookup registrado para el tipo {type.Name}.") { }
}
```

> **El único cast feo está encapsulado** dentro de `FindAsync<T>`, que es seguro porque el índice se
> construyó justo con ese tipo. El código que **usa** el resolver (`FindAllAsync<Ingredient>(ids)`)
> trabaja con genéricos fuertemente tipados — nunca ve un cast ni un `object`.

## Una implementación: `IngredientLookup`

El agregado `Ingredient` es destino de FK desde `Pizza`, así que registra su lookup. Reutiliza el
puerto de lectura que ya tiene del núcleo (6.3):

```csharp
namespace ShopMicro.Catalog.Ingredient.Persistence;

using ShopMicro.Core.Lookup;
using ShopMicro.Catalog.Ingredient.Domain;

/// <summary>
/// Lookup de Ingredient. Se apoya en IGetIngredient (puerto de lectura del núcleo),
/// que ya lanza EntityNotFoundException si el id no existe.
/// </summary>
public sealed class IngredientLookup : ILookup<Ingredient>
{
    private readonly IGetIngredient _get;

    public IngredientLookup(IGetIngredient get) => _get = get;

    public Task<Ingredient> FindAsync(Guid id) => _get.GetAsync(id);
}
```

Al ser async de extremo a extremo, el lookup simplemente **reenvía** el `GetAsync` del puerto: sin
adaptadores ni bloqueos, la tarea se propaga tal cual hasta el llamante.

## Uso en el handler de crear pizza

Aquí se cierra el círculo. El handler resuelve los ids → ingredientes y construye el agregado con
la **fábrica** (que sí emite el evento, lección 6.4):

```csharp
namespace ShopMicro.Catalog.Pizza.Features.Create;

using ShopMicro.Core.Lookup;
using ShopMicro.Catalog.Ingredient.Domain;
using ShopMicro.Catalog.Pizza.Domain;
using ShopMicro.Catalog.Pizza.Persistence;

public sealed class Handler
{
    private readonly IAddPizza _repository;
    private readonly LookupResolver _resolver;

    public Handler(IAddPizza repository, LookupResolver resolver)
    {
        _repository = repository;
        _resolver = resolver;
    }

    public async Task<Response> HandleAsync(Command command)
    {
        // ids → entidades de dominio (lanza 404 si algún ingrediente no existe)
        ISet<Ingredient> ingredients = await _resolver.FindAllAsync<Ingredient>(command.IngredientIds);

        // construir con la FÁBRICA: emite PizzaCreated
        var pizza = Pizza.Create(command.Name, command.Description, command.Url, ingredients);

        await _repository.AddAsync(pizza);
        return new Response(pizza.Id);
    }
}

public sealed record Command(string Name, string Description, string Url, IReadOnlyList<Guid> IngredientIds);
public sealed record Response(Guid Id);
```

El handler **no conoce** `IngredientLookup` ni ningún lookup concreto: solo habla con
`LookupResolver`. Si mañana la pizza referencia también `Salsa`, el handler haría
`_resolver.FindAllAsync<Salsa>(...)` y bastaría con **registrar** un `ILookup<Salsa>` — sin tocar el
resolver ni este handler.

## Registro en DI (la inyección de colección)

Cada lookup se registra **por su marcadora**, de modo que el resolver los recibe todos con una sola
consulta al contenedor. Nada de registrar `object`:

```csharp
// Cada agregado destino de FK registra su lookup, expuesto como ILookupMarker
builder.Services.AddScoped<ILookupMarker, IngredientLookup>();
// ... futuros: AddScoped<ILookupMarker, SalsaLookup>(), etc.

// El resolver recibe TODOS los lookups del contenedor vía la marcadora
builder.Services.AddScoped<LookupResolver>(sp =>
    new LookupResolver(sp.GetServices<ILookupMarker>()));
```

El contenedor recoge **solo** lo etiquetado con `ILookupMarker` — nunca tipos ajenos. Añadir un
destino de FK nuevo es una línea de registro más; el resolver no se toca.

---

## Por qué esto es Open/Closed

```
   AÑADIR un nuevo destino de FK (p. ej. Salsa)
   ───────────────────────────────────────────
   1. Crear  SalsaLookup : ILookup<Salsa>
   2. Registrarlo en DI

   Lo que NO se toca:
   ✗ LookupResolver        (cerrado a modificación)
   ✗ los handlers que usan el resolver
   ✗ los demás lookups

   El sistema queda ABIERTO a extensión (nuevos lookups) y
   CERRADO a modificación (el resolver no cambia nunca).
```

---

## Puntos clave

- **`Lookup` resuelve referencias (FKs) entre agregados**: traduce ids → entidades de dominio,
  verificando existencia.
- **`LookupResolver` es Open/Closed**: añadir un destino de FK = registrar un `ILookup<T>` nuevo,
  **sin modificar** el resolver ni los handlers que lo usan.
- La interfaz queda **limpia** (solo `FindAsync`): el tipo se **infiere del genérico**, no se
  declara dentro de la interfaz.
- Reutiliza la semántica de 6.3: **`FindAsync` lanza** si no existe; `FindAllAsync` falla entera si
  falta un id (sin resultados parciales).
- El **cast inseguro queda encapsulado** en el resolver; los llamantes usan genéricos
  fuertemente tipados.
