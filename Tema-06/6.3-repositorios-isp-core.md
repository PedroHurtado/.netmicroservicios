# 6.3 — Repositorios con ISP: el núcleo reutilizable

> **Módulo 6 · Lección 3 de 9** · ★ **Núcleo del módulo**
> **Duración estimada:** ~45 min
> **Tipo:** Teoría + código

---

## La idea en una frase

> En lugar de un `IRepository<T>` gigante con `Add`, `Get`, `Update`, `Remove`, `GetAll`,
> `Exists`… que **todos** los repositorios heredan aunque no lo usen, definimos **una interfaz por
> operación** y cada repositorio **compone solo las que necesita**.

Eso es el **Principio de Segregación de Interfaces (ISP)**, la "I" de SOLID:

> *"Ningún cliente debería verse obligado a depender de métodos que no usa."*

Y vamos a ver que, lejos de complicar nada, **simplifica** la capa de datos y la hace honesta:
un repositorio que solo sabe añadir y leer **declara exactamente eso**, ni un método más.

---

## El error que estamos evitando

El repositorio genérico clásico:

```csharp
// ❌ El "God repository": todos lo heredan, casi nadie lo usa entero
public interface IRepository<T, TId>
{
    Task AddAsync(T entity);
    Task<T> GetAsync(TId id);
    Task UpdateAsync(T entity);
    Task RemoveAsync(TId id);
    Task<IReadOnlyList<T>> GetAllAsync();
    Task<bool> ExistsAsync(TId id);
    // ... y sigue creciendo
}
```

Problemas:

- Un repositorio de "solo lectura" se ve **obligado a implementar** `AddAsync`, `UpdateAsync`,
  `RemoveAsync` (típicamente lanzando `NotSupportedException` — un olor a diseño).
- El cliente que solo necesita leer **depende** de toda la superficie de escritura.
- La interfaz **nunca deja de crecer**, y cada método nuevo afecta a todos los implementadores.

---

## La alternativa: cuatro acciones atómicas

Definimos cuatro interfaces, **una operación cada una**, en el núcleo del servicio
(`Core/Repository`):

```csharp
namespace ShopMicro.Core.Repository;

/// <summary>Acción de añadir. Añadir no requiere leer, por eso NO extiende IGet.</summary>
public interface IAdd<in T>
{
    Task AddAsync(T entity);
}
```

```csharp
namespace ShopMicro.Core.Repository;

/// <summary>
/// Acción de leer por id. <c>GetAsync</c> devuelve <c>T</c> o lanza
/// <see cref="EntityNotFoundException"/>; nunca devuelve null ni un tipo opcional.
/// </summary>
public interface IGet<T, in TId>
{
    Task<T> GetAsync(TId id);
}
```

```csharp
namespace ShopMicro.Core.Repository;

/// <summary>
/// Acción de borrar. Extiende IGet: para borrar, primero hay que garantizar que existe.
/// </summary>
public interface IRemove<T, TId> : IGet<T, TId>
{
    Task RemoveAsync(TId id);
}
```

```csharp
namespace ShopMicro.Core.Repository;

/// <summary>
/// Acción de actualizar. Extiende IGet: para actualizar, primero hay que leer.
/// </summary>
public interface IUpdate<T, TId> : IGet<T, TId>
{
    Task UpdateAsync(T entity);
}
```

### Las dependencias entre interfaces no son arbitrarias

Fíjate en **quién extiende a quién** — es una decisión de diseño que codifica reglas de negocio:

```
        IAdd<T>          (añadir no necesita leer → independiente)

        IGet<T,TId>      (leer es la operación base)
          ▲   ▲
          │   │
  IRemove │   │ IUpdate  (borrar y actualizar EXIGEN leer primero:
          │   │           hay que garantizar que la entidad existe)
```

- **`IAdd` no extiende `IGet`**: para añadir una entidad nueva no hace falta leer nada.
- **`IRemove` e `IUpdate` extienden `IGet`**: no puedes borrar ni actualizar algo cuya existencia
  no has comprobado. La herencia de interfaces **expresa esa precondición** en el sistema de tipos.

---

## El contrato que conecta dominio e infraestructura

Hasta aquí, las interfaces solo hablan de **dominio** (`T`, `TId`). Para implementarlas sobre EF
Core necesitamos dos cosas: el `DbSet`/`DbContext` y un **mapper** dominio ↔ persistencia. Las
declaramos en un contrato común:

```csharp
namespace ShopMicro.Core.Repository;

/// <summary>
/// Contrato común de los mappers dominio ↔ EF. Permite que las interfaces base
/// mapeen genéricamente sin conocer el tipo concreto.
/// </summary>
/// <typeparam name="T">tipo de dominio</typeparam>
/// <typeparam name="TEf">tipo de persistencia (entidad EF)</typeparam>
public interface IMapper<T, TEf>
{
    TEf ToEf(T domain);
    T ToDomain(TEf ef);
}
```

```csharp
namespace ShopMicro.Core.Repository;

using Microsoft.EntityFrameworkCore;

/// <summary>
/// Base "sin herencia" de los repositorios EF. Aporta los dos únicos puntos
/// variables que cada repositorio concreto debe cablear: el DbContext, el DbSet
/// y el mapper.
/// </summary>
/// <typeparam name="T">tipo de dominio (extiende EntityBase para extraer el id)</typeparam>
/// <typeparam name="TId">tipo del id</typeparam>
/// <typeparam name="TEf">tipo de persistencia</typeparam>
public interface IRepositoryEf<T, TId, TEf>
    where T : EntityBase<TId>
    where TEf : class
{
    DbContext Db();              // unidad de trabajo (SaveChangesAsync)
    DbSet<TEf> Set();            // la "tabla"
    IMapper<T, TEf> Mapper();    // dominio ↔ EF
}
```

> **Comparación con Java.** En Spring Data el punto variable era un `JpaRepository<J, ID>`
> inyectado. Aquí el equivalente es el par `DbContext` + `DbSet<TEf>`: el `DbSet` da las consultas
> (`FindAsync`, LINQ) y el `DbContext` da el commit (`SaveChangesAsync`). Es la diferencia de fondo
> entre los dos ORMs, y queda **encapsulada** en esta única interfaz.

## La pieza clave de C#: *default interface methods*

Desde **C# 8**, una interfaz puede aportar **implementación por defecto** de sus métodos. Esto es
el equivalente exacto de los `default methods` de Java que usábamos en el curso de Spring Boot, y
es lo que nos permite **escribir la lógica de cada operación una sola vez** y reutilizarla por
composición, **sin herencia de clases**.

Una interfaz `*Ef` por cada acción, que **compone** `IRepositoryEf` + la acción correspondiente e
implementa el método como `default`:

```csharp
namespace ShopMicro.Core.Repository;

using Microsoft.EntityFrameworkCore;

/// <summary>Implementa IAdd.AddAsync como default, componiendo IRepositoryEf + IAdd.</summary>
public interface IAddEf<T, TId, TEf> : IRepositoryEf<T, TId, TEf>, IAdd<T>
    where T : EntityBase<TId>
    where TEf : class
{
    async Task IAdd<T>.AddAsync(T entity)
    {
        await Set().AddAsync(Mapper().ToEf(entity));
        await Db().SaveChangesAsync();
    }
}
```

```csharp
namespace ShopMicro.Core.Repository;

using Microsoft.EntityFrameworkCore;

/// <summary>Implementa IGet.GetAsync como default: mapea a dominio o lanza si no existe.</summary>
public interface IGetEf<T, TId, TEf> : IRepositoryEf<T, TId, TEf>, IGet<T, TId>
    where T : EntityBase<TId>
    where TEf : class
{
    /// <summary>Tipo de dominio, usado para construir la excepción cuando no se encuentra.</summary>
    Type DomainType() => typeof(T);

    async Task<T> IGet<T, TId>.GetAsync(TId id)
    {
        var ef = await Set().FindAsync(id);
        if (ef is null)
            throw new EntityNotFoundException(DomainType(), id!);
        return Mapper().ToDomain(ef);
    }
}
```

```csharp
namespace ShopMicro.Core.Repository;

using Microsoft.EntityFrameworkCore;

/// <summary>
/// Implementa IRemove.RemoveAsync como default. Extiende IGetEf para garantizar
/// existencia (y lanzar si no) antes del borrado.
/// </summary>
public interface IRemoveEf<T, TId, TEf> : IGetEf<T, TId, TEf>, IRemove<T, TId>
    where T : EntityBase<TId>
    where TEf : class
{
    async Task IRemove<T, TId>.RemoveAsync(TId id)
    {
        await GetAsync(id);                  // lanza EntityNotFoundException si no existe
        var ef = await Set().FindAsync(id);
        Set().Remove(ef!);
        await Db().SaveChangesAsync();
    }
}
```

```csharp
namespace ShopMicro.Core.Repository;

using Microsoft.EntityFrameworkCore;

/// <summary>
/// Implementa IUpdate.UpdateAsync como default. Extiende IGetEf para reutilizar su
/// GetAsync (garantiza existencia antes de guardar).
/// </summary>
public interface IUpdateEf<T, TId, TEf> : IGetEf<T, TId, TEf>, IUpdate<T, TId>
    where T : EntityBase<TId>
    where TEf : class
{
    async Task IUpdate<T, TId>.UpdateAsync(T entity)
    {
        await GetAsync(entity.Id);           // lanza EntityNotFoundException si no existe
        Set().Update(Mapper().ToEf(entity));
        await Db().SaveChangesAsync();
    }
}
```

> **Detalle de C#.** Implementamos los métodos como **explícitos de interfaz**
> (`Task IAdd<T>.AddAsync(...)`). Es la forma de proveer el cuerpo `default` para un método que
> viene de *otra* interfaz heredada. El efecto es idéntico a los `default methods` de Java:
> la lógica vive en la interfaz, no en una clase base.

## EntityBase y la excepción

Dos piezas de apoyo en el núcleo del dominio (`Core/Domain`):

```csharp
namespace ShopMicro.Core.Domain;

/// <summary>Raíz de las entidades de dominio. Expone el id para las operaciones genéricas.</summary>
public abstract class EntityBase<TId>
{
    public TId Id { get; protected set; } = default!;
}
```

```csharp
namespace ShopMicro.Core.Domain;

/// <summary>Se lanza cuando una entidad no existe. La capa de errores la traduce a 404.</summary>
public sealed class EntityNotFoundException : Exception
{
    public EntityNotFoundException(Type domainType, object id)
        : base($"{domainType.Name} con id '{id}' no encontrado.") { }
}
```

> Esto encaja con el Módulo 3: `EntityNotFoundException` se mapea a un `ProblemDetails` con
> `status: 404` en el manejador global de errores. La capa de datos **lanza**, la capa web
> **traduce**.

## Lo que hemos ganado

```
   Repositorio que solo lee:        implements IGetEf
   Repositorio de solo escritura:   implements IAddEf
   Repositorio CRUD completo:       implements IAddEf, IGetEf, IUpdateEf, IRemoveEf
```

Cada repositorio **declara en su firma exactamente lo que sabe hacer**. No hay métodos heredados
que lanzan `NotSupportedException`. No hay un cliente acoplado a operaciones que no usa. Y la
**implementación se escribió una sola vez**, en las interfaces `*Ef`.

---

## Puntos clave

- **ISP = una interfaz por operación.** `IAdd`, `IGet`, `IRemove`, `IUpdate`.
- La **herencia entre interfaces expresa precondiciones**: `IRemove`/`IUpdate` extienden `IGet`
  porque exigen que la entidad exista; `IAdd` no.
- Los **default interface methods de C#** (≥ C# 8) son el equivalente de los `default methods` de
  Java: implementación reutilizable **sin herencia de clases**.
- `IRepositoryEf` aísla los **dos únicos puntos variables**: el par `DbContext`/`DbSet` y el mapper.
- `GetAsync` **devuelve `T` o lanza** — nunca `null` ni tipos opcionales. La capa web traduce la
  excepción a 404.
