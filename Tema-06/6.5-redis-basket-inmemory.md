# 6.5 — Redis como almacén del Basket.API (en memoria)

> **Módulo 6 · Lección 5 de 9**
> **Duración estimada:** ~25 min
> **Tipo:** Código

---

## Otro servicio, otro estilo de almacén

El `Basket.API` (carrito de la compra) tiene un patrón de acceso muy distinto al de Catalog:

- Se lee y escribe **el carrito entero de un usuario**, identificado por su id.
- No hay consultas complejas ni relaciones: es un **clave → valor**.
- Los datos son **volátiles** y de vida corta (un carrito caduca).

Ese perfil es justo para lo que sirve **Redis**: un almacén clave-valor en memoria, rapidísimo.
En el curso "real" el Basket vive en Redis. **En este módulo lo sustituimos por un diccionario en
memoria**, por la misma razón que usamos InMemory en Catalog: queremos enseñar el **diseño**, no
aprovisionar un Redis.

Lo interesante: el **mismo principio ISP** del núcleo aplica aquí, aunque el almacén no sea EF.

## El dominio del carrito

```csharp
namespace ShopMicro.Basket.Domain;

public sealed class Basket
{
    private readonly List<BasketItem> _items = new();

    public Guid CustomerId { get; }
    public IReadOnlyList<BasketItem> Items => _items;

    public Basket(Guid customerId) => CustomerId = customerId;

    public void AddItem(Guid productId, string name, decimal price, int quantity)
    {
        var existing = _items.FirstOrDefault(i => i.ProductId == productId);
        if (existing is not null)
            existing.IncreaseQuantity(quantity);
        else
            _items.Add(new BasketItem(productId, name, price, quantity));
    }

    public decimal Total() => _items.Sum(i => i.Price * i.Quantity);
}

public sealed class BasketItem
{
    public Guid ProductId { get; }
    public string Name { get; }
    public decimal Price { get; }
    public int Quantity { get; private set; }

    public BasketItem(Guid productId, string name, decimal price, int quantity)
    {
        ProductId = productId;
        Name = name;
        Price = price;
        Quantity = quantity;
    }

    public void IncreaseQuantity(int by) => Quantity += by;
}
```

## El puerto: ISP también aquí

El carrito solo necesita dos operaciones: **leer** el carrito de un cliente y **guardarlo**
(crear o reemplazar). Definimos un puerto pequeño y honesto:

```csharp
namespace ShopMicro.Basket.Persistence;

using ShopMicro.Basket.Domain;

/// <summary>Lee el carrito de un cliente. Devuelve un carrito vacío si no existe.</summary>
public interface IGetBasket
{
    Task<Basket> GetAsync(Guid customerId);
}

/// <summary>Crea o reemplaza el carrito de un cliente (upsert).</summary>
public interface ISaveBasket
{
    Task SaveAsync(Basket basket);
}
```

> **Nota de diseño.** Aquí `GetAsync` **no lanza** si no existe: devuelve un carrito vacío. Es una
> regla de negocio distinta a la de Catalog (donde leer una pizza inexistente es un 404). El carrito
> "no creado todavía" es un estado **normal**, no un error. Mismo principio (puerto mínimo),
> distinta semántica según el dominio — y eso es correcto.

## La implementación en memoria

Un `ConcurrentDictionary` hace de "Redis". Implementa los dos puertos:

```csharp
namespace ShopMicro.Basket.Persistence;

using System.Collections.Concurrent;
using ShopMicro.Basket.Domain;

/// <summary>
/// Almacén del carrito en memoria. Sustituye a Redis en el aula. La interfaz pública
/// (IGetBasket, ISaveBasket) es idéntica a la que tendría una implementación Redis;
/// cambiar a Redis solo afecta a esta clase, no a quien la consume.
/// </summary>
public sealed class InMemoryBasketStore : IGetBasket, ISaveBasket
{
    private readonly ConcurrentDictionary<Guid, Basket> _store = new();

    public Task<Basket> GetAsync(Guid customerId)
    {
        var basket = _store.TryGetValue(customerId, out var found)
            ? found
            : new Basket(customerId);          // carrito vacío si no existe
        return Task.FromResult(basket);
    }

    public Task SaveAsync(Basket basket)
    {
        _store[basket.CustomerId] = basket;    // upsert
        return Task.CompletedTask;
    }
}
```

Registro en DI:

```csharp
builder.Services.AddSingleton<InMemoryBasketStore>();
builder.Services.AddSingleton<IGetBasket>(sp => sp.GetRequiredService<InMemoryBasketStore>());
builder.Services.AddSingleton<ISaveBasket>(sp => sp.GetRequiredService<InMemoryBasketStore>());
```

> Es `Singleton` (no `Scoped`) porque el diccionario **es** el almacén: debe sobrevivir entre
> peticiones. Con Redis sería `Scoped` (la conexión se gestiona aparte), pero los **puertos** que
> ve la aplicación no cambian.

## El día que quieras Redis de verdad

Solo cambia la implementación del puerto. Esquemáticamente:

```csharp
// Pseudocódigo: implementación Redis del MISMO puerto
public sealed class RedisBasketStore : IGetBasket, ISaveBasket
{
    private readonly IConnectionMultiplexer _redis;   // StackExchange.Redis

    public async Task<Basket> GetAsync(Guid customerId)
    {
        var json = await _redis.GetDatabase().StringGetAsync(customerId.ToString());
        return json.IsNullOrEmpty
            ? new Basket(customerId)
            : JsonSerializer.Deserialize<Basket>(json!)!;
    }

    public async Task SaveAsync(Basket basket)
    {
        var json = JsonSerializer.Serialize(basket);
        await _redis.GetDatabase().StringSetAsync(basket.CustomerId.ToString(), json);
    }
}
```

`IGetBasket` / `ISaveBasket` no cambian. Los handlers que los consumen **no se enteran**. Eso es lo
que nos da depender de **puertos pequeños** en lugar de un almacén concreto.

---

## Puntos clave

- El **mismo principio ISP** aplica fuera de EF: el Basket expone puertos mínimos
  (`IGetBasket`, `ISaveBasket`), no un repositorio genérico.
- La **semántica del `Get` depende del dominio**: en Catalog leer algo inexistente es un 404; en
  Basket es un carrito vacío (estado normal). El diseño se adapta al negocio.
- Sustituir Redis por un `ConcurrentDictionary` afecta **solo a la implementación del puerto**; los
  consumidores no cambian. Migrar a Redis real es reescribir una clase.
