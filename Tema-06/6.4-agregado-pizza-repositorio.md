## Dónde estamos

En 6.3 montamos el **núcleo reutilizable** (`IAdd`/`IGet`/`IRemove`/`IUpdate` + las `*Ef` con la
implementación por defecto). Ahora lo **aplicamos a un agregado concreto**: `Pizza`, con sus
`Ingredient` en relación N:M. Es exactamente el mismo agregado del curso de Spring Boot, trasladado
a .NET.

Vamos a ver cuatro piezas, en este orden:

```
   1. Dominio puro:        Pizza  (sin EF, con fábrica que emite evento + ctor de hidratación)
   2. Persistencia:        PizzaEf  (clase EF separada del dominio)
   3. Mapeo:               PizzaMapper  (manual, con Hydration → sin eventos al reconstruir)
   4. Vistas + repositorio: IAddPizza... + PizzaRepository
```

---

## Por qué una clase de persistencia SEPARADA del dominio

Esta es una **decisión de diseño explícita**
mapear el dominio `Pizza` directamente con EF Core. **No lo hacemos**, y conviene que el alumnado
entienda por qué:

- El agregado `Pizza` recibe sus ingredientes como un `IReadOnlySet<Ingredient>` y protege sus
  invariantes con constructores controlados. Configurar EF Core para que reconstruya **eso**
  (backing fields, navegaciones, constructor sin setters públicos) es **pelearse con el
  `DbContext`** sin necesidad.
- Es más sencillo —y más limpio— tener una **clase intermedia `PizzaEf`** pensada para EF (con sus
  setters, su `HashSet`, sus anotaciones/configuración) y un **mapper manual** que traduce en
  ambos sentidos.
- Beneficio extra: **el dominio queda 100% libre de EF.** No hay un solo `using
  Microsoft.EntityFrameworkCore` en la capa de dominio.

> Regla práctica: *la clase de dominio modela el negocio; la clase EF modela la fila de la tabla.*
> Son dos responsabilidades distintas y por eso son dos clases distintas.

## 1. El dominio: `Pizza` (recordatorio autocontenido)

El agregado de dominio. Lo importante para este módulo: tiene **dos vías de construcción**.

```csharp
namespace ShopMicro.Catalog.Pizza.Domain;

using ShopMicro.Core.Domain;

public class Pizza : EntityBase<Guid>
{
    private readonly HashSet<Ingredient> _ingredients;

    public string Name { get; private set; }
    public string Description { get; private set; }
    public string Url { get; private set; }
    public IReadOnlySet<Ingredient> Ingredients => _ingredients;

    // Eventos de dominio acumulados (lo trataremos a fondo con la mensajería).
    private readonly List<object> _events = new();
    public IReadOnlyList<object> Events => _events;
    public void ClearEvents() => _events.Clear();

    /// <summary>
    /// FÁBRICA: crea una pizza NUEVA. Emite el evento de dominio pizza.created.
    /// Es la única vía pública de creación.
    /// </summary>
    public static Pizza Create(string name, string description, string url,
                               IEnumerable<Ingredient> ingredients)
    {
        var pizza = new Pizza(Guid.NewGuid(), name, description, url, ingredients);
        pizza._events.Add(new PizzaCreated(pizza.Id, pizza.Name));   // ← emite evento
        return pizza;
    }

    /// <summary>
    /// CONSTRUCTOR DE HIDRATACIÓN (protected): reconstruye desde persistencia.
    /// NO emite eventos. Lo usará el mapper para volver de la BD al dominio.
    /// </summary>
    protected Pizza(Guid id, string name, string description, string url,
                    IEnumerable<Ingredient> ingredients)
    {
        Id = id;
        Name = name;
        Description = description;
        Url = url;
        _ingredients = new HashSet<Ingredient>(ingredients);
    }
}

public sealed record PizzaCreated(Guid PizzaId, string Name);
```



| Vía | Visibilidad | ¿Emite evento? | Uso |
|---|---|---|---|
| `Pizza.Create(...)` | pública (fábrica) | **Sí** (`PizzaCreated`) | Crear una pizza nueva en negocio |
| `protected Pizza(...)` | protegida | **No** | Reconstruir desde la BD (mapper) |

> **El problema que esto resuelve.** Si reconstruyéramos desde BD con la fábrica, **cada lectura
> dispararía un `PizzaCreated`** — un evento falso por cada `SELECT`. El constructor protegido de
> hidratación lo evita de raíz. (Es la alternativa, vista en clase, a llamar a `ClearEvents()`
> después de cada carga.)

## 2. La persistencia: `PizzaEf`

La clase que EF Core sí conoce. Modela la **fila** y la **relación N:M** con ingredientes. Tiene
setters y un constructor sin lógica de negocio: es un simple contenedor de datos.

```csharp
namespace ShopMicro.Catalog.Pizza.Persistence;

using ShopMicro.Catalog.Ingredient.Persistence;

/// <summary>
/// Entidad EF de Pizza. La relación con ingredientes se modela como N:M a través
/// de una tabla intermedia (configurada en el DbContext). Es un contenedor de datos:
/// sin invariantes ni eventos.
/// </summary>
public class PizzaEf
{
    public Guid Id { get; set; }
    public string Name { get; set; } = default!;
    public string Description { get; set; } = default!;
    public string Url { get; set; } = default!;

    public ICollection<IngredientEf> Ingredients { get; set; } = new HashSet<IngredientEf>();

    // Constructor sin parámetros requerido por EF Core
    public PizzaEf() { }

    public PizzaEf(Guid id, string name, string description, string url,
                   ICollection<IngredientEf> ingredients)
    {
        Id = id;
        Name = name;
        Description = description;
        Url = url;
        Ingredients = ingredients;
    }
}
```

La relación N:M se configuró en `OnModelCreating` (lección 6.2):

```csharp
modelBuilder.Entity<PizzaEf>()
    .HasMany(p => p.Ingredients)
    .WithMany();   // EF crea la tabla intermedia pizza_ingredient automáticamente
```

## 3. El mapeo: `PizzaMapper` con `Hydration`

El mapper manual dominio ↔ EF. La pieza fina es **cómo reconstruye el dominio sin emitir eventos**:
usando una subclase privada `Hydration` que invoca el **constructor protegido**.

```csharp
namespace ShopMicro.Catalog.Pizza.Persistence;

using ShopMicro.Core.Repository;
using ShopMicro.Catalog.Ingredient.Domain;
using ShopMicro.Catalog.Ingredient.Persistence;
using DomainPizza = ShopMicro.Catalog.Pizza.Domain.Pizza;

/// <summary>
/// Mapper manual Pizza ↔ PizzaEf. Se compone con IngredientMapper para mapear la
/// colección de ingredientes.
///
/// ToDomain reconstruye la pizza con la subclase Hydration, que invoca el
/// constructor protected de Pizza. Ese constructor NO emite eventos, de modo que
/// reconstruir desde BD no dispara pizza.created. Es la alternativa, vista en clase,
/// a llamar a ClearEvents() tras la fábrica.
/// </summary>
public sealed class PizzaMapper : IMapper<DomainPizza, PizzaEf>
{
    private readonly IngredientMapper _ingredientMapper;

    public PizzaMapper(IngredientMapper ingredientMapper)
        => _ingredientMapper = ingredientMapper;

    public PizzaEf ToEf(DomainPizza pizza)
    {
        var ingredients = pizza.Ingredients
            .Select(_ingredientMapper.ToEf)
            .ToHashSet();

        return new PizzaEf(pizza.Id, pizza.Name, pizza.Description, pizza.Url, ingredients);
    }

    public DomainPizza ToDomain(PizzaEf ef)
    {
        var ingredients = ef.Ingredients
            .Select(_ingredientMapper.ToDomain)
            .ToHashSet();

        return new Hydration(ef.Id, ef.Name, ef.Description, ef.Url, ingredients);
    }

    /// <summary>Subclase de hidratación: invoca el constructor protected → sin eventos.</summary>
    private sealed class Hydration : DomainPizza
    {
        public Hydration(Guid id, string name, string description, string url,
                         IEnumerable<Ingredient> ingredients)
            : base(id, name, description, url, ingredients) { }
    }
}
```

El `PizzaMapper`  con su `Hydration` interna. El truco
—subclase que abre el constructor protegido

## 4. Las vistas por agregado y el repositorio

### Vistas: tipos fijados, sin EF

Definimos "vistas" que **fijan los genéricos** del núcleo para `Pizza`. Solo
hablan de dominio; no saben nada de EF. Son los **puertos** que la aplicación inyecta (ISP en
acción: cada slice pide solo la vista que necesita).

```csharp
namespace ShopMicro.Catalog.Pizza.Persistence;

using ShopMicro.Core.Repository;
using DomainPizza = ShopMicro.Catalog.Pizza.Domain.Pizza;

/// <summary>Vista de "añadir pizza". Solo dominio, sin EF.</summary>
public interface IAddPizza : IAdd<DomainPizza> { }

/// <summary>Vista de "leer pizza por id". GetAsync lanza si no existe.</summary>
public interface IGetPizza : IGet<DomainPizza, Guid> { }

/// <summary>Vista de "actualizar pizza". Hereda GetAsync de IUpdate → IGet.</summary>
public interface IUpdatePizza : IUpdate<DomainPizza, Guid> { }

/// <summary>Vista de "borrar pizza". Hereda GetAsync de IRemove → IGet.</summary>
public interface IRemovePizza : IRemove<DomainPizza, Guid> { }
```

> Estas cuatro interfaces son la **superficie pública** de la persistencia hacia la aplicación. Un
> handler de "crear pizza" inyecta `IAddPizza`; uno de "ver pizza", `IGetPizza`. Nadie depende de
> más de lo que usa.

### El repositorio concreto

`PizzaRepository` **compone** las vistas + las `*Ef` del núcleo, cablea los tres puntos variables
(`Db()`, `Set()`, `Mapper()`) y **sobrescribe `GetAsync`** para cargar el agregado completo con
`Include` (el equivalente del `JOIN FETCH`).

```csharp
namespace ShopMicro.Catalog.Pizza.Persistence;

using Microsoft.EntityFrameworkCore;
using ShopMicro.Core.Repository;
using DomainPizza = ShopMicro.Catalog.Pizza.Domain.Pizza;

/// <summary>
/// Repositorio de Pizza. add/update/remove provienen de los default methods de las
/// interfaces *Ef; solo se sobrescribe GetAsync para cargar el agregado completo con
/// Include (evita que los ingredientes lleguen vacíos). Sobrescribir un default es
/// idéntico a sobrescribir un método heredado: el diseño lo permite cuando un caso
/// lo necesita.
/// </summary>
public sealed class PizzaRepository :
    IAddPizza, IGetPizza, IUpdatePizza, IRemovePizza,
    IAddEf<DomainPizza, Guid, PizzaEf>,
    IUpdateEf<DomainPizza, Guid, PizzaEf>,
    IRemoveEf<DomainPizza, Guid, PizzaEf>
{
    private readonly CatalogDbContext _db;
    private readonly PizzaMapper _mapper;

    public PizzaRepository(CatalogDbContext db, PizzaMapper mapper)
    {
        _db = db;
        _mapper = mapper;
    }

    // --- los tres puntos variables que exige IRepositoryEf ---
    public DbContext Db() => _db;
    public DbSet<PizzaEf> Set() => _db.Pizzas;
    public IMapper<DomainPizza, PizzaEf> Mapper() => _mapper;

    // --- único método sobrescrito: carga el agregado completo ---
    public async Task<DomainPizza> GetAsync(Guid id)
    {
        var ef = await _db.Pizzas
            .Include(p => p.Ingredients)        // ← equivalente al JOIN FETCH de JPA
            .FirstOrDefaultAsync(p => p.Id == id);

        if (ef is null)
            throw new EntityNotFoundException(typeof(DomainPizza), id);

        return _mapper.ToDomain(ef);
    }
}
```

Observa la **simetría exacta** con el `PizzaRepository` de Java:

| Java | .NET |
|---|---|
| `implements IAddPizza, ..., IAddJpa<...>` | `: IAddPizza, ..., IAddEf<...>` |
| `JpaRepository<PizzaJpa,UUID> jpa()` | `DbSet<PizzaEf> Set()` + `DbContext Db()` |
| `Mapper<Pizza,PizzaJpa> mapper()` | `IMapper<Pizza,PizzaEf> Mapper()` |
| `Class<Pizza> domainType()` | `typeof(Pizza)` (inline) |
| `findByIdWithIngredients` + `JOIN FETCH` | `.Include(p => p.Ingredients)` |
| override de `get` | override de `GetAsync` |

`AddAsync`, `UpdateAsync` y `RemoveAsync` **no se escriben aquí**: vienen de los default methods de
`IAddEf`, `IUpdateEf`, `IRemoveEf`. Solo `GetAsync` necesita lógica propia (el `Include`), así que
es lo único que el repositorio sobrescribe.

## Registro en el contenedor de DI

`Program.cs` de Catalog.API. Registramos el repositorio **una vez** y lo exponemos por **cada
vista** (así cada handler inyecta solo la que usa):

```csharp
builder.Services.AddScoped<PizzaMapper>();
builder.Services.AddScoped<IngredientMapper>();

builder.Services.AddScoped<PizzaRepository>();
builder.Services.AddScoped<IAddPizza>(sp => sp.GetRequiredService<PizzaRepository>());
builder.Services.AddScoped<IGetPizza>(sp => sp.GetRequiredService<PizzaRepository>());
builder.Services.AddScoped<IUpdatePizza>(sp => sp.GetRequiredService<PizzaRepository>());
builder.Services.AddScoped<IRemovePizza>(sp => sp.GetRequiredService<PizzaRepository>());
```

Y en un handler de un slice (estilo Vertical Slice del Módulo 3):

```csharp
public sealed class Handler
{
    private readonly IAddPizza _repository;   // ← solo la vista que necesita
    public Handler(IAddPizza repository) => _repository = repository;

    public async Task<Response> HandleAsync(Command command)
    {
        var pizza = Pizza.Create(command.Name, command.Description, command.Url, /* ... */);
        await _repository.AddAsync(pizza);
        return new Response(pizza.Id);
    }
}
```

## Puntos clave

- **Clase de persistencia separada del dominio**, decisión deliberada: evita pelearse con EF para
  reconstruir el agregado y mantiene el **dominio libre de EF**.
- El dominio tiene **dos vías de construcción**: fábrica pública (`Create`, emite evento) y
  **constructor protegido de hidratación** (no emite). El mapper usa la subclase `Hydration` para
  reconstruir **sin disparar eventos**.
- Las **vistas** (`IAddPizza`…) fijan los genéricos y son la superficie pública hacia la
  aplicación. Cada handler inyecta **solo la vista que usa** (ISP).
- `PizzaRepository` **compone** vistas + `*Ef`; hereda `add/update/remove` de los default methods y
  **solo sobrescribe `GetAsync`** para el `Include` (agregado completo).
- La traducción Java → .NET es **1:1**: `JOIN FETCH` → `Include`, `JpaRepository` → `DbSet`+
  `DbContext`, `default methods` → default interface methods.
