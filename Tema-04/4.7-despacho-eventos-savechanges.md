# Módulo 4 · Lección 4.7 — Despacho de eventos en `SaveChanges`

> **Duración estimada:** 50 min
> **Servicio del proyecto:** `ShopMicro.Infrastructure` (el `DbContext`)
> **Requisitos:** Lección 4.6 (el flujo de emisión), DI y MediatR

---

## 1. Dónde enganchamos el despacho

Tenemos agregados que acumulan eventos en memoria. La pregunta es: **¿en qué momento exacto
se publican esos eventos?**

La respuesta de ShopMicro: **justo dentro de `SaveChangesAsync`, antes del commit real.**
Sobrescribimos `SaveChangesAsync` en el `DbContext` para:

1. Recoger los agregados que tienen eventos pendientes.
2. Publicarlos uno a uno con MediatR.
3. Limpiar los eventos de cada agregado.
4. Llamar a `base.SaveChangesAsync()` —el único commit real.

> **¿Por qué un override y no un interceptor de EF Core?** Un `SaveChangesInterceptor` es
> perfectamente válido y, en producción, a menudo preferible (desacopla la lógica del
> `DbContext`). Pero para **enseñar el flujo** el override es más directo: todo el mecanismo
> está a la vista en un solo método, sin saltar a otra clase ni entender el ciclo de vida de
> los interceptores. Cuando el concepto está claro, migrar a interceptor es trivial.

## 2. El override paso a paso

```csharp
namespace ShopMicro.Infrastructure;

using MediatR;
using Microsoft.EntityFrameworkCore;
using ShopMicro.Domain;

public class ShopMicroDbContext(
    DbContextOptions<ShopMicroDbContext> options,
    IPublisher publisher) : DbContext(options)
{
    private readonly IPublisher _publisher = publisher;

    // ... DbSet<T> de las entidades del servicio ...

    public override async Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
    {
        await DispatchDomainEventsAsync(cancellationToken);
        return await base.SaveChangesAsync(cancellationToken);
    }

    private async Task DispatchDomainEventsAsync(CancellationToken cancellationToken)
    {
        // 1. Recoger los agregados con eventos pendientes.
        //    OJO: materializamos con ToList() ANTES de publicar (ver nota más abajo).
        var aggregates = ChangeTracker
            .Entries<IHasDomainEvents>()
            .Where(entry => entry.Entity.DomainEvents.Count > 0)
            .Select(entry => entry.Entity)
            .ToList();

        // 2. Aplanar todos los eventos de todos los agregados.
        var domainEvents = aggregates
            .SelectMany(aggregate => aggregate.DomainEvents)
            .ToList();

        // 3. Limpiar ANTES de publicar: si un handler vuelve a tocar el agregado,
        //    no reprocesamos los mismos eventos.
        aggregates.ForEach(aggregate => aggregate.Clear());

        // 4. Publicar cada evento con MediatR. Los handlers se ejecutan aquí,
        //    dentro de la misma transacción, antes del commit.
        foreach (var domainEvent in domainEvents)
        {
            await _publisher.Publish(domainEvent, cancellationToken);
        }
    }
}
```

## 3. Los dos detalles que SÍ importan

### 3.1 `ToList()` defensivo: la colección que muta mientras la recorres

Publicamos **antes** de `base.SaveChangesAsync()`. Eso significa que un handler del Camino 1
hará `Set<DomainEvent>().Add(...)` mientras seguimos dentro del bloque de despacho. Ese
`Add` **modifica el `ChangeTracker`**. Si estuviéramos iterando directamente sobre
`ChangeTracker.Entries<...>()` de forma perezosa, EF lanzaría una excepción de "colección
modificada durante la enumeración".

Por eso materializamos con `.ToList()` **antes** de empezar a publicar: congelamos la lista
de agregados y de eventos de *este* `SaveChanges`. Los nuevos registros del Outbox que
añadan los handlers se persistirán en el `base.SaveChangesAsync()` final, pero no entran en
el bucle de despacho actual.

### 3.2 `Clear()` antes de publicar, no después

Limpiamos los eventos del agregado **antes** del bucle de `Publish`. ¿Por qué? Porque un
handler podría, legítimamente, modificar el mismo agregado y volver a llamar a
`SaveChanges` en cadena. Si no hubiéramos limpiado, esos eventos seguirían en la colección y
se republicarían. Limpiar primero corta cualquier ciclo de reprocesamiento.

> Como ya **materializamos los eventos en `domainEvents`** (paso 2), limpiar la colección
> del agregado (paso 3) no nos quita nada: seguimos teniendo la lista para publicar.

## 4. El contrato `IHasDomainEvents`

Para que el `DbContext` pueda preguntar "¿este agregado tiene eventos?" sin conocer los
parámetros genéricos `<TId, TEventId>`, exponemos un contrato no genérico. Esto es **ISP**:
el `DbContext` solo necesita *leer eventos y limpiarlos*, nada más.

```csharp
namespace ShopMicro.Domain;

public interface IHasDomainEvents
{
    IReadOnlyList<object> DomainEvents { get; }
    void Clear();
}
```

Y la `AggregateRoot` lo implementa de forma explícita, adaptando su colección genérica al
contrato no genérico:

```csharp
public abstract class AggregateRoot<TId, TEventId>(TId id)
    : EntityBase<TId>(id), IHasDomainEvents
{
    private readonly List<DomainEvent<TEventId>> _domainEvents = [];

    public IReadOnlyList<DomainEvent<TEventId>> DomainEvents => _domainEvents.AsReadOnly();

    protected void Add(DomainEvent<TEventId> domainEvent) => _domainEvents.Add(domainEvent);
    protected void Remove(DomainEvent<TEventId> domainEvent) => _domainEvents.Remove(domainEvent);
    public void Clear() => _domainEvents.Clear();

    // --- Implementación explícita de IHasDomainEvents ---
    // El DbContext ve los eventos como object; no necesita conocer TEventId.
    IReadOnlyList<object> IHasDomainEvents.DomainEvents => _domainEvents.AsReadOnly();
}
```

> **Detalle sobre `IPublisher.Publish` y el tipo `object`.** MediatR despacha según el tipo
> **en tiempo de ejecución** del objeto publicado. Aunque el bucle reciba los eventos como
> `object`, MediatR resolverá el handler correcto para el tipo concreto de cada
> `DomainEvent`. Para que un `DomainEvent<TId>` sea publicable, debe implementar
> `INotification` (lo añadimos en la lección 4.8, donde definimos los handlers).

## 5. Por qué esto garantiza atomicidad

El orden es deliberado:

```
DispatchDomainEventsAsync   →  los handlers escriben en el ChangeTracker
                               (filas de Outbox, efectos del Camino 2)
                               PERO TODAVÍA NO HAY COMMIT
base.SaveChangesAsync()     →  AQUÍ se hace el ÚNICO commit:
                               estado del agregado + filas de Outbox + Camino 2
                               en una sola transacción de base de datos
```

Si `base.SaveChangesAsync()` falla, **nada** se persiste: ni el cambio de estado, ni las
filas del Outbox, ni el efecto local. No existe el escenario "guardé el evento pero no el
cambio que lo provocó". Esa es justamente la garantía que el patrón Outbox necesita, y la
obtenemos gratis por poner el despacho **antes** del commit y dentro del mismo `DbContext`.

---

## Puntos clave

- El despacho se engancha en un **override de `SaveChangesAsync`**: recoger → limpiar →
  publicar → commit. (Un interceptor es la evolución natural, pero el override enseña mejor.)
- **Materializa con `.ToList()` antes de publicar**: los handlers del Camino 1 añaden filas
  al `ChangeTracker` y modificarían la colección que estás recorriendo.
- **`Clear()` antes del bucle de `Publish`** para cortar reprocesamientos en cadena; los
  eventos ya están a salvo en una lista materializada.
- El `DbContext` depende de un contrato **`IHasDomainEvents` no genérico** (ISP): solo
  necesita leer y limpiar eventos.
- Publicar **antes** de `base.SaveChangesAsync()` mete los efectos de los handlers en la
  **misma transacción** → **un único commit atómico**.
