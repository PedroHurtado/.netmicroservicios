# Módulo 4 · Lección 4.5 — gRPC: contratos con Protobuf y comunicación de alto rendimiento

> **Duración estimada:** 55 min
> **Servicio del proyecto:** comunicación interna entre servicios de ShopMicro
> **Requisitos:** Lecciones 4.1–4.2 (síncrono, HTTP)

---

## 1. Dónde encaja gRPC

REST sobre HTTP/JSON es la lengua franca de las APIs públicas: universal, legible,
*cacheable*, perfecta de cara al cliente final. Pero **entre servicios internos**, donde el
emisor y el receptor son tuyos y las llamadas son muy frecuentes, JSON de texto y HTTP/1.1
dejan rendimiento sobre la mesa.

**gRPC** es una alternativa para esa comunicación **interna, de alto rendimiento y contrato
estricto**: usa HTTP/2 y serializa con **Protobuf** (binario y compacto en lugar de texto).

---

## 2. La idea: el contrato primero (`.proto`)

En REST el contrato es implícito (documentado, idealmente, con OpenAPI). En gRPC el contrato
es **un fichero `.proto`** del que se **genera código** para cliente y servidor. Una sola
fuente de verdad, fuertemente tipada, compartida por ambos extremos.

```protobuf
syntax = "proto3";

option csharp_namespace = "ShopMicro.Catalog.Grpc";

package catalog;

// El servicio y sus operaciones.
service CatalogGrpc {
  rpc GetProduct (ProductRequest) returns (ProductReply);
}

message ProductRequest {
  int32 product_id = 1;
}

message ProductReply {
  int32 id = 1;
  string name = 2;
  double price = 3;
  bool is_available = 4;
}
```

Los números (`= 1`, `= 2`) son las **etiquetas de campo**: identifican cada campo en el
formato binario. Son la clave de la **compatibilidad**: puedes añadir campos nuevos con
etiquetas nuevas sin romper a los consumidores antiguos, que simplemente los ignoran.

## 3. El servidor (en Catalog.API)

El generador de gRPC crea una clase base abstracta a partir del `.proto`; tú heredas e
implementas la lógica.

```csharp
namespace ShopMicro.Catalog.Grpc;

using Grpc.Core;

public sealed class CatalogGrpcService(IProductRepository repository)
    : CatalogGrpc.CatalogGrpcBase
{
    private readonly IProductRepository _repository = repository;

    public override async Task<ProductReply> GetProduct(
        ProductRequest request, ServerCallContext context)
    {
        var product = await _repository.GetByIdAsync(request.ProductId, context.CancellationToken);

        if (product is null)
            throw new RpcException(new Status(StatusCode.NotFound, "Producto no encontrado"));

        return new ProductReply
        {
            Id = product.Id,
            Name = product.Name,
            Price = (double)product.Price,
            IsAvailable = product.Stock > 0
        };
    }
}
```

Registro:

```csharp
// Program.cs de Catalog.API
builder.Services.AddGrpc();
// ...
app.MapGrpcService<CatalogGrpcService>();
```

## 4. El cliente (en Ordering.API)

El mismo `.proto` genera un cliente fuertemente tipado. Se integra con `HttpClientFactory`
—y por tanto con Polly, igual que en 4.4— vía `AddGrpcClient`:

```csharp
// Program.cs de Ordering.API
builder.Services
    .AddGrpcClient<CatalogGrpc.CatalogGrpcClient>(options =>
    {
        options.Address = new Uri(builder.Configuration["Services:Catalog:GrpcUrl"]!);
    })
    .AddStandardResilienceHandler();   // la misma resiliencia de 4.4
```

Uso:

```csharp
var reply = await _catalogGrpcClient.GetProductAsync(
    new ProductRequest { ProductId = command.ProductId },
    cancellationToken: cancellationToken);
```

## 5. REST vs. gRPC: cuándo cada uno

Esta es la decisión que los alumnos deben saber tomar. No es "gRPC mejor que REST"; es **cada
uno en su sitio**.

| Criterio | **REST / JSON** | **gRPC / Protobuf** |
|---|---|---|
| **Formato** | texto (JSON), legible | binario, compacto |
| **Transporte** | HTTP/1.1 (o 2) | HTTP/2 (multiplexado) |
| **Contrato** | implícito / OpenAPI | explícito (`.proto`), código generado |
| **Rendimiento** | bueno | superior (menos bytes, menos parsing) |
| **Streaming** | limitado | bidireccional nativo |
| **Navegador / público** | universal | requiere gRPC-Web / proxy |
| **Legibilidad / debug** | alta (curl, navegador) | baja (binario) |
| **Encaje ideal** | **APIs públicas, cara al cliente** | **servicio↔servicio interno, alto volumen** |

### Regla práctica para ShopMicro

- **El Gateway hacia el exterior y las APIs que consume el frontend** → REST. Universal y
  depurable.
- **Llamadas internas frecuentes y sensibles a latencia** entre servicios → candidatas a
  gRPC. Por ejemplo, si Ordering consultara Catalog miles de veces por minuto, gRPC reduce
  bytes y CPU frente a JSON.
- **Notificación de hechos** ("pedido creado") → ni REST ni gRPC: **asíncrono** por el broker
  (4.6–4.8). gRPC sigue siendo petición/respuesta síncrona; no sustituye a la mensajería.

> **Matiz honesto.** gRPC aporta de verdad cuando el volumen o la latencia lo justifican.
> Para una malla pequeña como ShopMicro en un curso, REST + Refit + Polly cubre casi todo
> con menos fricción. Presentamos gRPC para que los alumnos **sepan elegirlo cuando toque**,
> no para usarlo en todas partes. Meter gRPC donde no hace falta es complejidad sin retorno.

---

## Puntos clave

- **gRPC** = HTTP/2 + **Protobuf** (binario). Pensado para comunicación **interna
  servicio↔servicio** de **alto rendimiento**.
- El **contrato va primero**: un `.proto` del que se **genera** cliente y servidor tipados.
  Una sola fuente de verdad.
- Las **etiquetas de campo** (`= 1`, `= 2`) dan **compatibilidad**: añadir campos no rompe a
  los consumidores antiguos.
- El cliente gRPC se integra con **`HttpClientFactory`**, así que hereda la **resiliencia de
  Polly** igual que Refit.
- **REST para lo público y depurable; gRPC para lo interno de alto volumen; broker para
  notificar hechos.** gRPC sigue siendo síncrono: **no** sustituye a la mensajería asíncrona.
- En ShopMicro, gRPC se presenta para **saber elegirlo**, no como reemplazo universal de REST.
