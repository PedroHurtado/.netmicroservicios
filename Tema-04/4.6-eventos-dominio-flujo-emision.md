# Módulo 4 · Lección 4.6 — Eventos de dominio: el flujo de emisión

> **Duración estimada:** 45 min
> **Servicio del proyecto:** transversal (la infraestructura vive en `ShopMicro.Domain` + `ShopMicro.Infrastructure`)
> **Requisitos:** haber visto mensajería asíncrona (conceptos: *broker*, cola, *topic*, eventos) en 4.6 introductorio

---

## 1. Qué problema resolvemos

Cuando un agregado cambia de estado, a menudo *otras partes del sistema* necesitan
enterarse: otro caso de uso del mismo servicio, o incluso otro microservicio. La forma
ingenua —llamar directamente a esas otras partes desde el agregado o desde el handler del
comando— acopla el agregado a sus consumidores y mezcla responsabilidades.

Un **evento de dominio** invierte esa relación: el agregado se limita a **declarar que algo
ha ocurrido** ("el precio del producto ha cambiado", "se ha creado un pedido") y *no sabe
quién reaccionará*. Quien reacciona son los **EventHandlers**, registrados aparte.

La pregunta de esta lección no es *qué* es un evento de dominio (eso ya lo modelamos), sino
**cómo se emite**: desde que el agregado lo acumula hasta que alguien lo procesa.

---

## 2. Las piezas que ya tenemos

Partimos de dos clases que ya están definidas en el dominio de ShopMicro.

### 2.1 El evento de dominio

`DomainEvent<TId>` es **a su vez una entidad** (tiene identidad propia). El identificador es
genérico a propósito: cuando el evento se persista en un *outbox*, cada microservicio elige
el tipo de id que necesite (no se asume `Guid`). El `Payload` es `object`: puede ser un
`record`, una clase, o el propio agregado.

```csharp
namespace ShopMicro.Domain;

public enum DomainEventStatus
{
    Pending,
    Publish
}

public class DomainEvent<TId> : EntityBase<TId>
{
    public string EventType { get; }
    public string Aggregate { get; }
    public Guid IdAggregate { get; }
    public string User { get; }
    public DateTime TimeStamp { get; }
    public DomainEventStatus Status { get; protected set; }
    public object Payload { get; }

    protected DomainEvent(
        TId id, string eventType, string aggregate, Guid idAggregate,
        string user, DateTime timeStamp, object payload)
        : base(id)
    {
        EventType = eventType;
        Aggregate = aggregate;
        IdAggregate = idAggregate;
        User = user;
        TimeStamp = timeStamp;
        Status = DomainEventStatus.Pending;
        Payload = payload;
    }

    public static DomainEvent<TId> Create(
        TId id, string eventType, string aggregate, Guid idAggregate,
        string user, DateTime timeStamp, object payload)
        => new(id, eventType, aggregate, idAggregate, user, timeStamp, payload);

    public void MarkAsPublished() => Status = DomainEventStatus.Publish;
}
```

> **Detalle de diseño.** Constructor y atributos `protected`, datos expuestos solo por
> *getter*: el evento es **inmutable** una vez creado. Lo único que muta es el `Status`, y
> solo a través de `MarkAsPublished()`. Un evento es un hecho del pasado; un hecho no se
> reescribe.

### 2.2 La raíz de agregado

La `AggregateRoot` **acumula** los eventos que va generando. La colección se expone como
solo lectura: nadie de fuera puede manipular la lista directamente.

```csharp
namespace ShopMicro.Domain;

public abstract class AggregateRoot<TId, TEventId>(TId id) : EntityBase<TId>(id)
{
    private readonly List<DomainEvent<TEventId>> _domainEvents = [];

    public IReadOnlyList<DomainEvent<TEventId>> DomainEvents => _domainEvents.AsReadOnly();

    protected void Add(DomainEvent<TEventId> domainEvent) => _domainEvents.Add(domainEvent);

    protected void Remove(DomainEvent<TEventId> domainEvent) => _domainEvents.Remove(domainEvent);

    public void Clear() => _domainEvents.Clear();
}
```

> **Por qué dos parámetros de tipo.** `TId` es el id del agregado; `TEventId` es el id de
> los eventos. Son independientes porque **el outbox decide con qué tipo de id persiste cada
> evento**, y eso no tiene por qué coincidir con el id del agregado.

## 3. El flujo completo, de un vistazo

```
  Comando (Handler de la feature)
        │  agg.HacerAlgo()  → internamente agg.Add(evento)
        ▼
  El agregado acumula DomainEvents en memoria
        │
        ▼
  DbContext.SaveChangesAsync()
        │
        ├─ 1. Recoge los agregados que tienen DomainEvents
        ├─ 2. Publica cada evento con MediatR  ─────────────┐
        │                                                    │
        │      MediatR despacha a 1..N INotificationHandler  │
        │                                                    │
        │   ┌────────────────────────────┬───────────────────┴───────────┐
        │   │ CAMINO 1 (a otro servicio) │ CAMINO 2 (efecto local)        │
        │   │ el handler hace            │ el handler procesa el efecto   │
        │   │ Set<DomainEvent>().Add(e)  │ sobre ESTA misma DbContext     │
        │   │ → fila Outbox (Pending)    │ (cálculo, otra escritura...)   │
        │   └────────────────────────────┴────────────────────────────────┘
        │
        ├─ 3. Clear() de los eventos en cada agregado
        └─ 4. base.SaveChangesAsync()  ← UN ÚNICO COMMIT atómico
                                          (estado + outbox + camino 2)
        │
        ▼  (proceso aparte, en segundo plano)
  MessageRelay (BackgroundService)
        ├─ lee Outbox WHERE Status = Pending
        ├─ publica el mensaje al broker (RabbitMQ)
        └─ MarkAsPublished()  (Pending → Publish)
```

La idea que **debe quedar grabada**: el evento de dominio **no sabe cuál es su destino**. Esa
política la deciden los handlers. Por eso hay dos caminos posibles y ambos parten del mismo
punto.

---

## 4. Los dos caminos

Un mismo evento puede tener varios handlers, y cada handler elige qué hacer con él. En
ShopMicro distinguimos dos destinos:

| | **Camino 1 — Outbox → broker** | **Camino 2 — efecto local** |
|---|---|---|
| **Cuándo** | el efecto cruza la frontera del servicio (otro microservicio debe enterarse) | el efecto se queda dentro del servicio |
| **Qué hace el handler** | inserta el `DomainEvent` en la tabla Outbox | ejecuta el efecto sobre la misma `DbContext` |
| **Quién lo publica luego** | el `MessageRelay`, en segundo plano | nadie: ya está hecho al cerrar la transacción |
| **Garantía** | el evento no se pierde aunque el broker esté caído | atómico con el cambio de estado |

> **Punto innegociable del diseño.** Tanto la escritura en el Outbox (Camino 1) como el
> efecto local (Camino 2) ocurren **en la misma transacción** que el cambio de estado del
> agregado. Hay **un solo `SaveChanges` real** al final. Si algo falla, *todo* se revierte:
> el estado, la fila del outbox y el efecto local. No hay estados intermedios incoherentes.

Esto tiene una consecuencia que conviene decir en voz alta: **los handlers del Camino 2 no
deben tener efectos externos no transaccionales** (llamar por HTTP a otro servicio, enviar
un correo) ejecutados directamente. Si el efecto cruza la frontera del proceso, su sitio es
el Camino 1 (Outbox). El Camino 2 es para escrituras sobre la propia base de datos y
cálculos en memoria. Si más adelante necesitamos coordinar una operación entre servicios con
compensaciones, eso es un **Saga** (Módulo 6), no un handler in-process.

## Puntos clave

- Un **evento de dominio** es un *hecho del pasado*: inmutable, con identidad propia. El
  agregado lo **acumula**; no lo procesa.
- El agregado **no conoce a sus consumidores**. La política de "qué hacer con el evento"
  vive en los **EventHandlers**, no en el dominio.
- Hay **dos caminos** desde un evento: salir del servicio vía **Outbox → MessageRelay →
  broker** (Camino 1), o resolverse **localmente** sobre la misma `DbContext` (Camino 2).
- Todo —cambio de estado, escritura en Outbox y efecto local— ocurre en **una sola
  transacción** con **un único commit**. Atomicidad total o nada.
- Los efectos que **cruzan la frontera del servicio** van siempre por el Outbox, nunca como
  efecto in-process directo.
