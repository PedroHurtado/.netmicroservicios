# Módulo 4 · Lección 4.4 — Resiliencia con Polly: retry, timeout y circuit breaker

> **Duración estimada:** 55 min
> **Servicio del proyecto:** `Ordering.API` → `Catalog.API` (el cliente Refit de 4.3, ahora resiliente)
> **Requisitos:** Lección 4.3 (Refit sobre `HttpClientFactory`)

---

## 1. Por qué una llamada de red necesita defensas

La llamada Ordering → Catalog de 4.3 funciona... cuando todo va bien. Pero la red **no** va
siempre bien: un *timeout* esporádico, un reinicio de Catalog, una microcaída. Sin defensas,
cualquiera de esos hipos transitorios tumba la creación del pedido.

**Polly** añade políticas de resiliencia alrededor de la llamada HTTP. Las tres
fundamentales:

- **Retry** — reintenta ante fallos *transitorios* (puede que el segundo intento funcione).
- **Timeout** — corta una llamada que tarda demasiado (no esperes 30s a un servicio colgado).
- **Circuit breaker** — si Catalog falla repetidamente, **deja de llamarlo** un tiempo, para
  no añadir leña y para fallar rápido.

---

## 2. Las tres políticas, explicadas

### 2.1 Retry: reintentar lo transitorio

Un fallo **transitorio** (timeout puntual, 503 momentáneo) puede resolverse solo. Reintentar
tiene sentido. Un fallo **permanente** (404, 400) no: reintentar es desperdiciar tiempo.

La clave es el **backoff exponencial con jitter**: si reintentas inmediatamente y mil
clientes hacen lo mismo, machacas a Catalog justo cuando se recupera (*retry storm*).
Esperar 1s, 2s, 4s... con algo de aleatoriedad reparte la presión.

### 2.2 Timeout: no esperar indefinidamente

Hay dos niveles: el *timeout* por **intento** (esta llamada concreta no puede tardar más de
2s) y el total. Sin timeout, una llamada colgada retiene un hilo y, en cadena, propaga la
lentitud aguas arriba.

### 2.3 Circuit breaker: dejar de insistir

Si Catalog ha fallado, digamos, 5 veces seguidas, asumimos que está mal y **abrimos el
circuito**: durante un periodo, las llamadas fallan *inmediatamente* sin tocar la red. Tras
ese periodo, el circuito pasa a *half-open* y deja pasar una llamada de prueba: si va bien,
se cierra; si no, sigue abierto. Esto **da respiro al servicio caído** y evita que Ordering
malgaste recursos esperando.

```
   cerrado ──(N fallos seguidos)──► abierto
      ▲                                │
      │                          (pasa el tiempo)
      │                                ▼
      └──(prueba OK)──── half-open ◄───┘
                            │
                       (prueba KO)
                            ▼
                         abierto
```

## 3. Dos formas de aplicarlo en .NET 8

Polly v8 trae el concepto de `ResiliencePipeline`. Lo veremos de dos maneras:

1. **El pipeline explícito** — para que **veas el mecanismo** pieza a pieza.
2. **`AddStandardResilienceHandler`** — el atajo recomendado por Microsoft para producción.

Concepto primero, atajo después.

### 3.1 El pipeline explícito (para entender)

Se engancha al `IHttpClientBuilder` que nos devolvió `AddRefitClient` en 4.3:

```csharp
// Program.cs de Ordering.API
using Polly;
using Polly.Retry;
using Polly.Timeout;
using Polly.CircuitBreaker;

builder.Services
    .AddRefitClient<ICatalogApi>()
    .ConfigureHttpClient(client =>
    {
        client.BaseAddress = new Uri(builder.Configuration["Services:Catalog:BaseUrl"]!);
    })
    .AddResilienceHandler("catalog-pipeline", pipeline =>
    {
        // 1. Retry ante fallos transitorios, con backoff exponencial + jitter.
        pipeline.AddRetry(new HttpRetryStrategyOptions
        {
            MaxRetryAttempts = 3,
            BackoffType = DelayBackoffType.Exponential,
            UseJitter = true,
            Delay = TimeSpan.FromSeconds(1)
        });

        // 2. Circuit breaker: si falla el 50% de un volumen mínimo, abre 15s.
        pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions
        {
            FailureRatio = 0.5,
            MinimumThroughput = 10,
            SamplingDuration = TimeSpan.FromSeconds(30),
            BreakDuration = TimeSpan.FromSeconds(15)
        });

        // 3. Timeout por intento: ninguna llamada individual pasa de 2s.
        pipeline.AddTimeout(TimeSpan.FromSeconds(2));
    });
```

> **El orden importa.** Las estrategias se ejecutan como capas de cebolla, de fuera adentro
> en el orden en que se añaden. Retry **envuelve** al circuit breaker, que **envuelve** al
> timeout. Así: el timeout corta el *intento* individual; ese fallo lo cuenta el breaker; y
> el retry decide si reintentar. Si inviertes el orden, cambias la semántica —es un punto que
> conviene que los alumnos razonen, no que memoricen.

### 3.2 El atajo de producción

Microsoft empaqueta una configuración sensata de las tres (más rate limiting) en un solo
método. Es lo que usarías en el día a día:

```csharp
// Requiere el paquete Microsoft.Extensions.Http.Resilience
builder.Services
    .AddRefitClient<ICatalogApi>()
    .ConfigureHttpClient(client =>
    {
        client.BaseAddress = new Uri(builder.Configuration["Services:Catalog:BaseUrl"]!);
    })
    .AddStandardResilienceHandler();   // retry + breaker + timeout + rate limiter, con defaults razonables
```

Y se puede afinar:

```csharp
    .AddStandardResilienceHandler(options =>
    {
        options.Retry.MaxRetryAttempts = 4;
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(20);
    });
```

> **Cuál enseñar en clase.** Empieza por el pipeline explícito (3.1) para que los alumnos
> *vean* las tres estrategias y su orden. Cierra con `AddStandardResilienceHandler` (3.2)
> como "esto es lo que de verdad pondrás en producción, y ahora entiendes qué hace por
> dentro".

## 4. La pieza que Polly NO arregla: idempotencia

El **retry** reenvía la petición. Para una **lectura** (`GET /products/42`) eso es inofensivo:
pedir dos veces lo mismo da el mismo resultado. Pero si reintentaras una **escritura** no
idempotente (crear algo dos veces), el retry podría **duplicar** el efecto.

Por eso reintentar es seguro casi siempre en GET, y en operaciones de escritura hay que
diseñar la idempotencia (claves de idempotencia, *upserts*). Es el mismo principio que vimos
con el consumidor del Outbox en 4.8: **at-least-once exige idempotencia**. Aquí, nuestro caso
es un GET, así que reintentar es seguro de fábrica.

---

## 5. El resultado de la progresión 4.2 → 4.3 → 4.4

La misma llamada Ordering → Catalog ha pasado por tres estados:

```
4.2  HttpClientFactory   →  funciona, con boilerplate, frágil
4.3  + Refit             →  sin boilerplate (interface declarativa)
4.4  + Polly             →  resiliente (retry, timeout, circuit breaker)
```

Y el handler de `CreateOrder` **sigue sin enterarse**: pide `ICatalogClient` y ya está. Toda
la evolución ocurrió en la configuración y la infraestructura, nunca en la lógica de negocio.

---

## Puntos clave

- La red falla de forma **transitoria**; sin defensas, un hipo tumba la operación. Polly pone
  esas defensas alrededor de la llamada.
- **Retry** (con *backoff exponencial + jitter* para evitar *retry storms*), **timeout** (no
  esperar a un servicio colgado) y **circuit breaker** (dejar de llamar a lo que está roto,
  fallar rápido, dar respiro).
- Se engancha al **`IHttpClientBuilder` de Refit** (4.3): la resiliencia envuelve el mismo
  cliente, sin tocar al consumidor.
- **El orden de las estrategias cambia la semántica**: retry envuelve breaker envuelve
  timeout. Razonarlo, no memorizarlo.
- Empieza por el **pipeline explícito** (ves el mecanismo) y cierra con
  **`AddStandardResilienceHandler`** (lo de producción).
- **Retry solo es seguro si la operación es idempotente.** En GET lo es; en escrituras, hay
  que diseñarlo. Mismo principio que el at-least-once del Outbox.
