# Módulo 4 · Lección 4.8 — EventHandlers y MessageRelay

> **Duración estimada:** 55 min
> **Servicio del proyecto:** `ShopMicro.Infrastructure` (handlers + relay) · `Ordering.API` (ejemplo `OrderCreated`)
> **Requisitos:** Lección 4.7 (despacho en `SaveChanges`), MediatR, conceptos de broker / RabbitMQ

---

## 1. Cierre del flujo

En 4.7 dejamos el `DbContext` publicando cada `DomainEvent` con MediatR justo antes del
commit. Ahora escribimos **quién escucha** esos eventos (los `INotificationHandler`) y, para
el Camino 1, **quién drena el Outbox hacia el broker** (el `MessageRelay`).

Recordemos los dos caminos de la lección 4.6:

```
DomainEvent publicado con MediatR
   ├── Camino 1: handler → escribe en Outbox → (MessageRelay) → RabbitMQ
   └── Camino 2: handler → efecto local sobre la misma DbContext
```

---

## 2. El evento como `INotification`

Para que MediatR pueda despachar un `DomainEvent<TId>`, este debe implementar
`INotification`. Lo añadimos a la clase base; así **todos** los eventos de dominio son
publicables sin tocar cada uno.

```csharp
namespace ShopMicro.Domain;

using MediatR;

public class DomainEvent<TId> : EntityBase<TId>, INotification
{
    // ... resto idéntico a la lección 4.6 ...
}
```

> **Nota de capas.** Esto introduce una dependencia de `MediatR.Contracts` (no de MediatR
> completo) en el proyecto de dominio. `INotification` es solo un *marker interface* sin
> comportamiento. Si te incomoda tocar el dominio, la alternativa es envolver el
> `DomainEvent` en un `record NotificationWrapper(object Event) : INotification` en
> infraestructura y publicar el wrapper. En el curso elegimos el marker directo por
> simplicidad; lo señalamos para que la decisión sea consciente.

---

## 3. Camino 1 — el handler que escribe en el Outbox

Como el `DomainEvent<TId>` **es** la entidad del Outbox (se mapea directamente a la tabla),
este handler no transforma nada: simplemente lo registra en el `DbSet`. Al estar dentro del
despacho de `SaveChanges`, esa inserción entra en la **misma transacción**.

```csharp
namespace ShopMicro.Infrastructure.EventHandlers;

using MediatR;
using ShopMicro.Domain;

// Handler para los eventos que deben SALIR del servicio.
// Recibe el evento concreto (aquí, el de Ordering con id Guid).
public sealed class OrderCreatedToOutboxHandler(ShopMicroDbContext dbContext)
    : INotificationHandler<OrderCreated>
{
    private readonly ShopMicroDbContext _dbContext = dbContext;

    public Task Handle(OrderCreated notification, CancellationToken cancellationToken)
    {
        // El evento ES la fila del Outbox: lo añadimos al DbSet tal cual.
        // No hay commit aquí; lo hará el base.SaveChangesAsync() de la lección 4.7.
        _dbContext.Set<DomainEvent<Guid>>().Add(notification);
        return Task.CompletedTask;
    }
}
```

> **Mapeo EF Core del Outbox.** La tabla Outbox guarda los campos del `DomainEvent`
> (`EventType`, `Aggregate`, `IdAggregate`, `User`, `TimeStamp`, `Status`) y el `Payload`
> serializado a JSON (`jsonb` en PostgreSQL). El `Status` arranca en `Pending`. Configuramos
> la conversión del `Payload` con un `ValueConverter` a `string`; lo detallamos en el Módulo
> 6 (EF Core con PostgreSQL), aquí basta con saber que la fila queda persistida.

## 4. Camino 2 — el handler de efecto local

Este handler resuelve el efecto **dentro del servicio**, sobre la misma `DbContext`. No
toca el Outbox ni el broker. Ejemplo: cuando se crea un pedido, marcar como reservado algún
contador interno (efecto que vive en la misma base de datos del servicio de pedidos).

```csharp
namespace ShopMicro.Infrastructure.EventHandlers;

using MediatR;

public sealed class OrderCreatedLocalHandler(ShopMicroDbContext dbContext)
    : INotificationHandler<OrderCreated>
{
    private readonly ShopMicroDbContext _dbContext = dbContext;

    public Task Handle(OrderCreated notification, CancellationToken cancellationToken)
    {
        // Efecto sobre ESTA misma DbContext. Entra en la misma transacción.
        // Sin llamadas HTTP ni envíos de correo: si el efecto cruza la
        // frontera del servicio, su sitio es el Outbox (Camino 1), no aquí.
        // ... lógica local sobre el modelo del servicio ...
        return Task.CompletedTask;
    }
}
```

> **Un evento, varios handlers.** `OrderCreated` tiene **dos** handlers registrados: el del
> Outbox y el local. MediatR los ejecuta a ambos cuando el `DbContext` publica el evento.
> Cada uno decide su destino sin que el otro lo sepa. Ahí está la potencia del patrón: la
> política de reacción está **distribuida en handlers**, no concentrada en el agregado.

## 5. El MessageRelay: drenar el Outbox hacia RabbitMQ

Hasta aquí, el Camino 1 solo ha *guardado* el evento en una tabla. Falta **publicarlo al
broker**. Eso lo hace un `BackgroundService` que se ejecuta en segundo plano,
independientemente de la petición que originó el evento.

```csharp
namespace ShopMicro.Infrastructure.Messaging;

using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using ShopMicro.Domain;

public sealed class MessageRelay(
    IServiceProvider serviceProvider,
    IEventBus eventBus) : BackgroundService
{
    private static readonly TimeSpan PollingInterval = TimeSpan.FromSeconds(5);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await DrainOutboxAsync(stoppingToken);
            await Task.Delay(PollingInterval, stoppingToken);
        }
    }

    private async Task DrainOutboxAsync(CancellationToken cancellationToken)
    {
        // Scope propio: el BackgroundService es singleton, el DbContext es scoped.
        using var scope = serviceProvider.CreateScope();
        var dbContext = scope.ServiceProvider.GetRequiredService<ShopMicroDbContext>();

        // 1. Leer los pendientes (orden de inserción → orden de publicación).
        var pending = await dbContext.Set<DomainEvent<Guid>>()
            .Where(e => e.Status == DomainEventStatus.Pending)
            .OrderBy(e => e.TimeStamp)
            .Take(50)
            .ToListAsync(cancellationToken);

        if (pending.Count == 0)
            return;

        // 2. Publicar cada uno al broker y marcarlo como publicado.
        foreach (var domainEvent in pending)
        {
            await eventBus.PublishAsync(domainEvent, cancellationToken);
            domainEvent.MarkAsPublished();   // Pending → Publish
        }

        // 3. Persistir los cambios de Status.
        await dbContext.SaveChangesAsync(cancellationToken);
    }
}
```

`IEventBus` es la abstracción del broker; su implementación con RabbitMQ + MassTransit es la
de las lecciones 4.6–4.7 de mensajería. Aquí nos basta su contrato:

```csharp
namespace ShopMicro.Infrastructure.Messaging;

public interface IEventBus
{
    Task PublishAsync<TEvent>(TEvent @event, CancellationToken cancellationToken)
        where TEvent : class;
}
```

## 6. Garantías y límites del relay

Conviene ser honesto con los alumnos sobre qué garantiza este relay sencillo y qué no:

- **At-least-once, no exactly-once.** Si el proceso muere *después* de `PublishAsync` pero
  *antes* de `SaveChangesAsync`, ese evento se volverá a publicar en la próxima vuelta. El
  consumidor debe ser **idempotente**. Es el comportamiento estándar y aceptable de un
  Outbox; lo exactly-once no existe en sistemas distribuidos sin coste enorme.
- **Orden aproximado.** Ordenamos por `TimeStamp`, suficiente para el curso. El orden
  estricto entre eventos de distintos agregados no está garantizado y rara vez se necesita.
- **Polling, no push.** Sondeamos cada 5s. Para producción se puede bajar el intervalo o
  combinar con notificaciones, pero el polling es robusto y fácil de razonar.

> **Por qué un proceso aparte y no publicar al broker dentro de `SaveChanges`.** Si
> publicáramos a RabbitMQ dentro de la transacción y el broker estuviera caído, fallaría el
> `SaveChanges` entero —perderíamos también el cambio de estado. Separar la escritura
> (transaccional, en la DB del servicio) de la publicación (en segundo plano, reintentable)
> es **exactamente** lo que el patrón Outbox resuelve.

## 7. Registro en el contenedor de DI

```csharp
// Program.cs del servicio (p.ej. Ordering.API)

// MediatR escanea el ensamblado donde viven los handlers.
builder.Services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssemblyContaining<OrderCreatedToOutboxHandler>());

// El DbContext (con IPublisher inyectado, ver lección 4.7).
builder.Services.AddDbContext<ShopMicroDbContext>(/* ... PostgreSQL ... */);

// El relay como servicio en segundo plano.
builder.Services.AddHostedService<MessageRelay>();

// El bus concreto (RabbitMQ + MassTransit) detrás de IEventBus.
builder.Services.AddSingleton<IEventBus, RabbitMqEventBus>();
```

## Puntos clave

- El `DomainEvent<TId>` implementa **`INotification`** para que MediatR lo despache; un
  marker interface sin comportamiento.
- **Camino 1**: el handler añade el evento al `DbSet` del Outbox —como el evento *es* la fila,
  no hay mapeo— y entra en la **misma transacción** del `SaveChanges`.
- **Camino 2**: el handler resuelve el efecto sobre la misma `DbContext`; nada que cruce la
  frontera del servicio.
- **Un evento, varios handlers**: MediatR ejecuta todos; la política de reacción está
  repartida en los handlers, no en el agregado.
- El **`MessageRelay`** es un `BackgroundService` que sondea el Outbox, publica los
  `Pending` al broker y los marca `Publish`. Necesita su **propio scope** de DI.
- Garantía **at-least-once** → los consumidores deben ser **idempotentes**. Separar
  escritura de publicación es la razón de ser del Outbox.
