# Módulo 4 · Lección 4.2 — Comunicación HTTP con `HttpClientFactory`: la forma base

> **Duración estimada:** 50 min
> **Servicio del proyecto:** `Ordering.API` consumiendo `Catalog.API`
> **Requisitos:** Lección 4.1; DI (Módulo 2)

---

## 1. El caso que nos acompañará en 4.2 → 4.3 → 4.4

Antes de crear un pedido, **Ordering.API necesita confirmar que el producto existe** (y, de
paso, traer su precio actual). Esa información vive en Catalog.API. Es una consulta puntual
cuya respuesta necesitamos *ahora* para decidir → comunicación **síncrona** por HTTP.

Vamos a implementar esa llamada tres veces, cada una mejor que la anterior:

- **4.2 (esta):** a mano, con `HttpClientFactory`. Para entender la base.
- **4.3:** con Refit, eliminando el *boilerplate*.
- **4.4:** con Polly, haciéndola resiliente.

---

## 2. Por qué NO se hace `new HttpClient()`

El error clásico del principiante:

```csharp
// ❌ NO hagas esto.
public async Task<bool> ExistsAsync(int productId)
{
    using var client = new HttpClient();   // un socket nuevo cada vez
    var response = await client.GetAsync($"https://catalog/products/{productId}");
    return response.IsSuccessStatusCode;
}
```

Dos problemas graves: **agotamiento de sockets** (cada `new HttpClient` abre conexiones que
el `using` no libera de inmediato; bajo carga te quedas sin puertos) y, paradójicamente, si
lo haces *singleton* para evitar lo anterior, **no detecta cambios de DNS**. `HttpClient`
está diseñado para reutilizarse, pero su ciclo de vida es delicado.

`IHttpClientFactory` resuelve ambos: gestiona un *pool* de `HttpMessageHandler` reutilizables
con rotación controlada. **Siempre** se accede a `HttpClient` a través de la factoría.

---

## 3. Typed Client: la forma recomendada

De las tres formas que ofrece la factoría (básico, *named*, *typed*), usamos **typed client**:
una clase fuertemente tipada que encapsula las llamadas a un servicio concreto. Encaja con la
inyección de dependencias y mantiene la URL base y la configuración en un solo sitio.

### 3.1 El contrato (en la capa de aplicación de Ordering)

Siguiendo ISP, la interfaz declara **solo lo que Ordering necesita** de Catalog, no un
cliente genérico:

```csharp
namespace Ordering.Application.Catalog;

public interface ICatalogClient
{
    Task<ProductInfo?> GetProductAsync(int productId, CancellationToken cancellationToken);
}

public sealed record ProductInfo(int Id, string Name, decimal Price, bool IsAvailable);
```

### 3.2 La implementación (typed client en infraestructura)

```csharp
namespace Ordering.Infrastructure.Catalog;

using System.Net;
using System.Net.Http.Json;
using Ordering.Application.Catalog;

public sealed class CatalogClient(HttpClient httpClient) : ICatalogClient
{
    private readonly HttpClient _httpClient = httpClient;

    public async Task<ProductInfo?> GetProductAsync(
        int productId, CancellationToken cancellationToken)
    {
        var response = await _httpClient.GetAsync(
            $"products/{productId}", cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadFromJsonAsync<ProductInfo>(
            cancellationToken: cancellationToken);
    }
}
```

> Fíjate: la URL es **relativa** (`products/{id}`). La base (`https://catalog/`) se configura
> una sola vez al registrar el cliente. El typed client no sabe *dónde* está Catalog; eso es
> configuración, no código.

## 4. Registro en DI

```csharp
// Program.cs de Ordering.API
builder.Services.AddHttpClient<ICatalogClient, CatalogClient>(client =>
{
    client.BaseAddress = new Uri(builder.Configuration["Services:Catalog:BaseUrl"]!);
    client.Timeout = TimeSpan.FromSeconds(10);
});
```

`AddHttpClient<TInterface, TImplementation>` hace dos cosas a la vez: registra el typed
client en el contenedor **y** lo conecta a la factoría, que le inyectará un `HttpClient`
correctamente gestionado. A partir de aquí, cualquier handler de Ordering puede pedir
`ICatalogClient` por constructor.

## 5. Uso desde un handler de comando

```csharp
namespace Ordering.Features.CreateOrder;

// Dentro del Handler del slice CreateOrder (Vertical Slice + Nested Classes)
public async Task<Response> Handle(Command command, CancellationToken cancellationToken)
{
    var product = await _catalogClient.GetProductAsync(command.ProductId, cancellationToken);

    if (product is null || !product.IsAvailable)
        throw new ProductNotAvailableException(command.ProductId);

    // ... crear el pedido con el precio traído de Catalog ...
}
```

## 6. Lo que todavía falta (y motiva 4.3 y 4.4)

Esta versión funciona, pero arrastra problemas que iremos resolviendo:

- **Boilerplate**: construir URLs a mano, comprobar status codes, deserializar. Multiplícalo
  por cada endpoint de cada servicio. → **4.3 (Refit)** lo elimina.
- **Frágil ante fallos**: si Catalog da un *timeout* puntual o un error transitorio, la
  llamada muere sin reintentar. No hay *circuit breaker*. → **4.4 (Polly)** lo arregla.

---

## Puntos clave

- **Nunca `new HttpClient()`**: agota sockets; en *singleton*, ignora cambios de DNS. Usa
  **`IHttpClientFactory`** siempre.
- El **typed client** encapsula las llamadas a un servicio en una clase tipada, integrada con
  DI; la **URL base y el timeout son configuración**, no código.
- El contrato (`ICatalogClient`) declara **solo lo que el consumidor necesita** (ISP), no un
  cliente HTTP genérico.
- `AddHttpClient<I, Impl>` registra el typed client **y** lo enchufa a la factoría en una
  línea.
- Esta forma base **funciona pero tiene boilerplate y es frágil**: 4.3 quita el boilerplate,
  4.4 añade resiliencia.
