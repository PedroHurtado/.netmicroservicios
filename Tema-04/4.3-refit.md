# Módulo 4 · Lección 4.3 — Refit: clientes HTTP declarativos por interface

> **Duración estimada:** 45 min
> **Servicio del proyecto:** `Ordering.API` consumiendo `Catalog.API` (mismo caso que 4.2)
> **Requisitos:** Lección 4.2 (typed client con `HttpClientFactory`)

---

## 1. La idea: describir, no implementar

En 4.2 escribimos a mano la construcción de la URL, la comprobación del status code y la
deserialización. **Refit** invierte el enfoque: tú **declaras** una interface con atributos
que describen las peticiones HTTP, y Refit **genera** la implementación por ti en tiempo de
compilación (*source generator*).

Es exactamente el mismo principio que ya aplicas con las interfaces de repositorio: defines
el *qué*, no el *cómo*. Aquí el "cómo" (montar la petición, parsear la respuesta) lo pone
Refit.

---

## 2. El antes y el después

**Antes (4.2):** una clase `CatalogClient` con un método que construye la petición, mira el
`NotFound`, llama a `EnsureSuccessStatusCode`, deserializa. ~15 líneas por endpoint.

**Después (Refit):** una interface. Cero líneas de implementación.

```csharp
namespace Ordering.Infrastructure.Catalog;

using Refit;
using Ordering.Application.Catalog;

public interface ICatalogApi
{
    [Get("/products/{productId}")]
    Task<ProductInfo?> GetProductAsync(int productId, CancellationToken cancellationToken);
}
```

El atributo `[Get("/products/{productId}")]` mapea el parámetro `productId` al segmento de la
URL por nombre. Refit genera el código que hace la llamada y deserializa la respuesta JSON a
`ProductInfo`.

> **Manejo del 404.** Por defecto Refit lanza `ApiException` ante un status de error. Para que
> un 404 devuelva `null` en lugar de excepción, el tipo de retorno puede ser
> `Task<ProductInfo?>` con la opción de tratar el contenido nulo, o se captura `ApiException`
> con `StatusCode == NotFound`. En el curso lo resolvemos en el adaptador (punto 4).

---

## 3. ¿Y nuestro contrato `ICatalogClient`?

Aquí hay una decisión de diseño importante. Tenemos **dos interfaces** que parecen
solaparse:

- `ICatalogClient` — el contrato **de la capa de aplicación**, expresado en el lenguaje de
  Ordering (definido en 4.2).
- `ICatalogApi` — el contrato **técnico de Refit**, que describe los endpoints HTTP de
  Catalog.

**No son lo mismo y conviene no fusionarlos.** `ICatalogClient` pertenece al dominio de la
aplicación: Ordering pide "dame la info de este producto" sin saber que por debajo hay HTTP.
`ICatalogApi` es un detalle de infraestructura: la forma de la API REST de Catalog. Mantener
ambos preserva la regla de dependencias (la aplicación no depende de Refit).

El puente entre ambos es un **adaptador**:

```csharp
namespace Ordering.Infrastructure.Catalog;

using System.Net;
using Refit;
using Ordering.Application.Catalog;

// Implementa el contrato de aplicación apoyándose en el cliente Refit.
public sealed class CatalogClientAdapter(ICatalogApi api) : ICatalogClient
{
    private readonly ICatalogApi _api = api;

    public async Task<ProductInfo?> GetProductAsync(
        int productId, CancellationToken cancellationToken)
    {
        try
        {
            return await _api.GetProductAsync(productId, cancellationToken);
        }
        catch (ApiException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
    }
}
```

> **¿Es imprescindible el adaptador?** No siempre. Si no te importa que la capa de aplicación
> conozca Refit, puedes registrar `ICatalogApi` directamente y usarlo en los handlers. Pero
> en un curso que enseña capas limpias, el adaptador muestra **dónde cortar la dependencia**:
> Refit queda confinado en infraestructura. Decide según cuánta pureza quieras en cada
> servicio.

## 4. Registro en DI

Refit se integra con `HttpClientFactory`: `AddRefitClient` devuelve un `IHttpClientBuilder`,
el mismo que en 4.2. Esto es **clave para 4.4**: la resiliencia se engancha aquí.

```csharp
// Program.cs de Ordering.API
using Refit;

builder.Services
    .AddRefitClient<ICatalogApi>()
    .ConfigureHttpClient(client =>
    {
        client.BaseAddress = new Uri(builder.Configuration["Services:Catalog:BaseUrl"]!);
        client.Timeout = TimeSpan.FromSeconds(10);
    });

// El adaptador que expone el contrato de aplicación.
builder.Services.AddScoped<ICatalogClient, CatalogClientAdapter>();
```

El handler de `CreateOrder` **no cambia ni una línea** respecto a 4.2: sigue pidiendo
`ICatalogClient`. Hemos cambiado la implementación por debajo sin tocar a quien la usa. Eso
es trabajar contra abstracciones.

---

## 5. Qué ganamos y qué cuesta

| | **Typed client manual (4.2)** | **Refit (4.3)** |
|---|---|---|
| Líneas por endpoint | ~15 | 1 (la firma) |
| Construcción de URL | a mano | por atributos |
| Deserialización | explícita | automática |
| Dependencia extra | ninguna | paquete `Refit` |
| Control fino del request | total | alto, pero vía atributos/opciones |

Refit brilla cuando consumes **muchos** endpoints de un servicio. Para una sola llamada
trivial, el typed client manual puede bastar. En ShopMicro, donde Ordering hablará con varios
servicios, Refit paga su coste rápido.

---

## Puntos clave

- Refit te deja **declarar** la API como una interface con atributos; **genera** la
  implementación. Mismo principio que tus interfaces de repositorio: defines el *qué*.
- Separa **dos contratos**: `ICatalogClient` (lenguaje de la aplicación) e `ICatalogApi`
  (endpoints HTTP de Refit). Un **adaptador** los une y **confina Refit en infraestructura**.
- `AddRefitClient<T>` devuelve un `IHttpClientBuilder` integrado con `HttpClientFactory`: la
  base sobre la que 4.4 montará la resiliencia.
- El **consumidor (`ICatalogClient`) no se entera del cambio**: cambiamos la implementación
  sin tocar los handlers.
- Refit gana cuanto **más endpoints** consumes; para una llamada aislada, el typed client
  manual es defendible.
