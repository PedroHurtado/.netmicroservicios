# 7.5 — Instrumentar con OpenTelemetry

> **Módulo 7 · Lección 5 de 8**
> Aquí está tu trabajo real en observabilidad. OpenTelemetry es el estándar para
> que tu servicio emita señales. Qué te viene gratis, qué instrumentas a mano, y
> cómo se exporta.

---

## Qué es OpenTelemetry (y por qué te ahorra elegir)

**OpenTelemetry** (OTel) es el estándar abierto y neutral para generar y exportar telemetría
—trazas, métricas y logs—. Su gracia: instrumentas tu código **una vez**, contra una API
estándar, y puedes exportar a **cualquier** backend (Jaeger, Prometheus, el que use tu empresa)
sin tocar el código. Se acabó atarse a un proveedor concreto.

Para .NET, OTel se apoya en primitivas que ya existían en el framework (`Activity` para trazas,
`Meter` para métricas), así que mucho de lo que necesitas **ya está generándose**; solo hay que
recogerlo y exportarlo.

---

## Lo primero que debes entender: instrumentación automática vs. manual

Esta distinción es la que decide cuánto trabajo tienes.

**Instrumentación automática** — viene en las **librerías de instrumentación** de OTel. Sin
que escribas nada, captura las cosas estándar:

- Cada petición HTTP entrante (ASP.NET Core) → un span automático.
- Cada llamada HTTP saliente (`HttpClient`) → un span automático.
- Cada llamada gRPC → un span automático.
- Consultas a base de datos (EF Core) → spans automáticos.

Esto cubre **la mayoría** de lo que necesitas en distribuido: los saltos entre servicios se
trazan solos. Para un servicio típico de ShopMicro, la instrumentación automática ya te da la
foto del viaje de la petición casi entera.

**Instrumentación manual** — la añades tú cuando quieres trazar algo **propio del negocio** que
las librerías no conocen: "validar el stock", "calcular el descuento", "publicar el evento de
pedido". Son operaciones tuyas, así que tienes que marcarlas tú.

```
   Automática (gratis):   HTTP in │ HTTP out │ gRPC │ EF Core
   Manual (tú):           "validar stock" │ "aplicar descuento" │ lógica de negocio
```

La regla práctica: **empieza solo con la automática.** Cubre casi todo. Añade spans manuales
solo donde la automática deje un hueco que de verdad te interese medir.

## Configurar OTel en el servicio

En el `Program.cs`, registrar OTel con las instrumentaciones automáticas y el exportador:

```csharp
builder.Services.AddOpenTelemetry()
    .ConfigureResource(r => r.AddService("catalog-api"))   // nombre del servicio en las trazas
    .WithTracing(tracing =>
    {
        tracing
            // Instrumentación automática:
            .AddAspNetCoreInstrumentation()   // peticiones entrantes
            .AddHttpClientInstrumentation()   // llamadas HTTP salientes
            .AddGrpcClientInstrumentation()   // llamadas gRPC salientes
            .AddEntityFrameworkCoreInstrumentation()  // consultas EF Core

            // Exportar al colector (su dirección viene dada por config).
            .AddOtelExporter(builder.Configuration["Otel:Endpoint"]);
            // p. ej. "http://jaeger:4317" del docker-compose
    });
```

> El nombre exacto del método exportador depende del paquete (`AddOtlpExporter`); la idea es la
> misma: **a dónde envío las trazas**, leído de configuración, no hardcodeado. En local apunta a
> tu Jaeger de compose; en producción, al colector que dé plataforma.

Con esto, sin una línea más, tu servicio ya traza todas sus peticiones, llamadas salientes y
consultas a BD, y las exporta. Eso es el 80% del valor por el 5% del esfuerzo.

## Añadir un span manual (cuando lo necesitas)

Para trazar una operación de negocio propia, creas un `Activity` (el span de .NET):

```csharp
// Un ActivitySource por servicio/módulo, estático.
private static readonly ActivitySource Activity = new("Catalog.API");

public async Task<bool> CheckStockAsync(Guid productId, int qty, CancellationToken ct)
{
    // Abre un span hijo del span actual de la petición.
    using var span = Activity.StartActivity("check-stock");
    span?.SetTag("product.id", productId);   // enriquecer con datos útiles
    span?.SetTag("requested.qty", qty);

    var stock = await _repository.GetStockAsync(productId, ct);
    var available = stock >= qty;

    span?.SetTag("stock.available", available);
    return available;
}
```

El `using` cierra el span automáticamente al salir, registrando su duración. Como está dentro
de la petición, OTel lo encadena como **hijo** del span de la petición: en Jaeger lo verás
anidado bajo ella. Y para que OTel recoja tu `ActivitySource`, lo registras:
`tracing.AddSource("Catalog.API")`.

---

## Sobre `SetTag`: enriquecer con cuidado

Los tags (atributos) hacen una traza útil: `product.id`, `requested.qty`, `stock.available` te
dejan filtrar y entender qué pasó. **Pero** —y esto enlaza con la lección 7.7— hay que pensar
qué metes ahí. Un tag con datos de negocio internos es oro para depurar **dentro** de tu
sistema, pero puede ser información que **no debe salir** si la traza cruza fronteras. Lo
veremos en detalle en 7.7. De momento, retén: **enriquece, pero con intención.**

---

## Lo que te llevas de esta lección

- **OpenTelemetry** es el estándar neutral: instrumentas una vez, exportas a cualquier backend.
- **Instrumentación automática** (HTTP in/out, gRPC, EF Core) cubre casi todo **sin escribir
  código**: empieza solo con ella.
- **Instrumentación manual** (un `ActivitySource` + `StartActivity`) la añades solo para
  operaciones **de negocio** que te interese medir.
- El exportador apunta al **colector que viene dado**, leído de configuración, nunca hardcodeado.
- Enriquece spans con **tags**, pero con criterio sobre qué información incluyes (preludio de
  7.7).
