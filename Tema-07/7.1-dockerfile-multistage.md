# 7.1 — Empaquetar el servicio: Dockerfile multi-stage

> **Módulo 7 · Lección 1 de 8**
> Tu servicio tiene que viajar al clúster como una imagen de contenedor. El
> Dockerfile es lo que tú escribes y mantienes. Vamos etapa por etapa.

---

## Qué problema resuelve un contenedor

Un contenedor empaqueta tu servicio **con todo lo que necesita para ejecutarse** —el runtime
de .NET, tus DLLs, las dependencias— en una unidad que corre igual en tu máquina, en CI y en
el clúster. Se acabó el "en mi máquina funciona".

El **Dockerfile** es la receta para construir esa imagen. Y aquí aparece la primera decisión
de diseño que sí es tuya: **multi-stage**.

---

## Por qué multi-stage: el problema de la imagen gorda

Para **compilar** una app .NET necesitas el **SDK**: compilador, herramientas, restauración de
paquetes. Es grande (cientos de MB). Pero para **ejecutar** la app ya compilada solo necesitas
el **runtime**, que es mucho más pequeño.

Si construyes y ejecutas en la misma imagen, te llevas el SDK entero a producción: una imagen
enorme, con compiladores y herramientas que no usas y que además **amplían la superficie de
ataque** (más cosas instaladas = más posibles vulnerabilidades).

La solución es **multi-stage**: una etapa con el SDK que **compila**, y otra etapa con solo el
runtime que **se queda con el resultado** y tira el resto. La imagen final lleva únicamente lo
necesario para correr.

```
   ┌─────────────────────────────┐
   │  Etapa BUILD (SDK, grande)   │   restaura, compila, publica
   │  compilador + herramientas   │
   └──────────────┬──────────────┘
                  │  copia SOLO la app publicada
                  ▼
   ┌─────────────────────────────┐
   │ Etapa RUNTIME (runtime, fino)│   ← esta es la imagen final
   │  solo lo necesario para correr│
   └─────────────────────────────┘
```

---

## El Dockerfile, etapa por etapa

Para Catalog.API:

```dockerfile
# ───────────────────────────────────────────────────────────
# Etapa 1: BUILD — usa el SDK completo para compilar y publicar
# ───────────────────────────────────────────────────────────
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# 1a. Copiar SOLO el .csproj y restaurar primero.
#     Truco de caché: si el .csproj no cambia, Docker reutiliza
#     la capa de restore y no vuelve a bajar paquetes en cada build.
COPY ["Catalog.API/Catalog.API.csproj", "Catalog.API/"]
RUN dotnet restore "Catalog.API/Catalog.API.csproj"

# 1b. Ahora sí, copiar el resto del código y compilar.
COPY . .
WORKDIR "/src/Catalog.API"
RUN dotnet build "Catalog.API.csproj" -c Release -o /app/build

# ───────────────────────────────────────────────────────────
# Etapa 2: PUBLISH — genera los artefactos listos para ejecutar
# ───────────────────────────────────────────────────────────
FROM build AS publish
RUN dotnet publish "Catalog.API.csproj" -c Release -o /app/publish \
    /p:UseAppHost=false

# ───────────────────────────────────────────────────────────
# Etapa 3: RUNTIME — imagen final, solo el runtime ASP.NET Core
# ───────────────────────────────────────────────────────────
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app

# Copiar SOLO lo publicado desde la etapa anterior. El SDK se queda atrás.
COPY --from=publish /app/publish .

# El puerto que expone el servicio dentro del contenedor.
EXPOSE 8080

# Comando de arranque.
ENTRYPOINT ["dotnet", "Catalog.API.dll"]
```

## Las etapas, en limpio

| Etapa | Imagen base | Qué hace | Por qué |
|---|---|---|---|
| **build** | `sdk:8.0` (grande) | restore + build | necesita compilador y herramientas |
| **publish** | hereda de build | `dotnet publish` | genera los artefactos finales |
| **final** | `aspnet:8.0` (fina) | copia lo publicado y arranca | solo runtime, imagen mínima |

Los dos detalles que marcan la diferencia y que conviene fijar:

1. **Restaurar antes de copiar todo el código.** Copiar primero el `.csproj`, restaurar, y
   *luego* copiar el resto. Así, mientras no cambien las dependencias, Docker reutiliza la capa
   de restore desde caché y los builds vuelan. Si copias todo de golpe, cualquier cambio en un
   `.cs` invalida la restauración y se rebaja todo otra vez.

2. **`COPY --from=publish`** es el corazón del multi-stage: la imagen final **solo** se lleva
   los artefactos publicados. El SDK, el código fuente y las herramientas se quedan en las
   etapas anteriores, que se descartan.

---

## Lo que controlas tú aquí

El Dockerfile es **código del repositorio**, tuyo. Las decisiones que tomas:

- Qué imagen base de runtime (versión, variante).
- El orden de las capas para aprovechar la caché.
- Qué puerto expone, qué variables por defecto, el `ENTRYPOINT`.

Lo que **no** decides aquí: cómo se despliega esa imagen, en qué nodo corre, cuántas réplicas.
Eso es plataforma, y lo toca el Módulo en su parte de K8s (7.3). Tú entregas una imagen limpia;
ellos la orquestan.

## Un paso más allá: ¿y si no fuera runtime, sino binario puro?

La imagen final que acabamos de construir lleva el **runtime** de ASP.NET Core (`aspnet:8.0`).
Tu código viaja como IL —bytecode— y se compila a código máquina **al arrancar**, mediante el
JIT (*Just-In-Time*). Funciona, es lo estándar, y es lo que vas a usar el 99% del tiempo.

Pero .NET ofrece un escalón más: **Native AOT** (*Ahead-Of-Time*). En lugar de viajar como IL y
compilarse al arrancar, tu servicio se compila a **código máquina nativo en tiempo de build**.
El resultado es un **binario puro**: sin IL, sin JIT, sin el runtime gestionado completo dentro.
Lo más parecido a un ejecutable al estilo Go o Rust que da el ecosistema .NET.

### Qué se gana con binario puro

| Aspecto | Runtime + JIT (lo actual) | Native AOT (binario puro) |
|---|---|---|
| **Arranque** | Hay que JIT-compilar al iniciar | Casi instantáneo (ya es nativo) |
| **Memoria** | Mayor (runtime + JIT en memoria) | Menor (sin JIT, sin metadata extra) |
| **Tamaño de imagen** | Lleva el runtime ASP.NET Core | Mínima: puede ir sobre `runtime-deps` o incluso *distroless* |
| **Superficie de ataque** | Runtime completo presente | Solo lo que el binario necesita |
| **Compilación** | Rápida | Lenta, y específica de plataforma (`-r linux-x64`) |

El arranque casi instantáneo y la memoria reducida son enormes justo en el contexto de este
módulo: contenedores que escalan a cero y arrancan bajo demanda, alta densidad de pods, entornos
*serverless*. Un servicio que arranca en milisegundos en lugar de cientos de milisegundos cambia
las reglas del escalado. Y la imagen, al no necesitar el runtime gestionado, puede bajar a una
base aún más mínima que el `aspnet:8.0` de nuestro Dockerfile — refuerza, llevándola al extremo,
la misma lógica del multi-stage: *llevar a producción solo lo imprescindible*.

Activarlo es, en apariencia, trivial. En el `.csproj`:

```xml
<PropertyGroup>
  <PublishAot>true</PublishAot>
</PropertyGroup>
```

### El detalle incómodo: nuestro propio stack lo está fastidiando

Si fuera tan fácil como esa línea, lo daríamos por hecho y a otra cosa. No lo es. Native AOT
tiene una condición innegociable: **prohíbe la reflexión que descubre tipos en runtime y la
generación de código al vuelo**. Y resulta que **varias piezas centrales del stack que estamos
usando en ShopMicro hacen exactamente eso**, así que rompen:

| Pieza de nuestro stack | ¿Compila a binario puro? | Por qué |
|---|---|---|
| **Minimal API** | ✅ Sí | El generador de delegados produce el enrutado sin reflexión |
| **gRPC** | ✅ Sí | Soporte AOT oficial |
| **EF Core** | ❌ **No** (sin más) | Construye el modelo por **reflexión** al arrancar |
| **MediatR** | ❌ **No** | Descubre handlers y aplica pipelines por **reflexión** y *assembly scanning* |
| **AutoMapper** *(si se usara)* | ❌ **No** | Genera los mappers **en runtime**; es incompatible con AOT *por diseño* |

Lee la tabla despacio, porque cuenta algo: **lo que bloquea el binario puro no es ASP.NET Core**.
La capa web (Minimal API, gRPC) está lista. **Lo que lo fastidia son las librerías que se apoyan
en magia de runtime**: descubrir tipos, escanear ensamblados, generar código al vuelo. Justo las
comodidades que nos ahorran *boilerplate* en desarrollo son las que impiden el binario nativo en
despliegue.

Y hay un patrón debajo, que conviene ver: **todas las que rompen, rompen por la misma razón**
—reflexión y/o código en runtime— y **todas tienen una salida idéntica** —mover ese trabajo a
**tiempo de compilación** con *source generators*—. Existen reemplazos source-generated para casi
todo (mappers generados, *mediators* generados, acceso a datos sin reflexión). El mismo principio
que hace un servicio observable y predecible —*que lo que ocurre sea visible y deliberado, no
deducido en caliente*— es el que lo hace compilable a nativo.

> **Para pensar:** la decisión de meter una librería que "lo resuelve sola por reflexión" tiene un
> coste que no se ve en desarrollo y aparece en el despliegue. ¿Compensa la comodidad de hoy el
> techo que pone mañana? No hay respuesta única —depende del servicio, del equipo, de si el
> arranque nativo es un requisito real o un lujo—. Pero la peor opción es no haberlo decidido:
> arrastrar la dependencia por inercia y descubrir el muro el día que alguien escribe
> `PublishAot`.

Para este curso seguimos con **runtime + JIT** (`aspnet:8.0`): es lo correcto para nuestro stack
y para aprender. Pero ahora sabéis que existe el escalón de arriba, qué se gana en él, y —sobre
todo— **qué piezas de nuestras propias elecciones nos cierran la puerta**.

---

## Lo que te llevas de esta lección

- Un contenedor empaqueta tu servicio con su runtime: corre igual en todas partes.
- **Multi-stage** separa **compilar** (SDK, grande) de **ejecutar** (runtime, fino): la imagen
  final es mínima y más segura.
- Las etapas: **build** → **publish** → **final**, donde final hace `COPY --from` de lo
  publicado y descarta el resto.
- **Restaura antes de copiar todo el código** para aprovechar la caché de capas de Docker.
- El Dockerfile es tuyo; el despliegue de la imagen es de plataforma.
- Existe un escalón más, **Native AOT** (binario puro): arranque casi instantáneo, menos memoria,
  imagen mínima. Pero **parte de nuestro stack (EF Core, MediatR) lo bloquea** por depender de
  reflexión en runtime; la salida del ecosistema es **source-generated**.
